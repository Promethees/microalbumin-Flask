# Rule_main.md — AI Coding Rules for the `main` Branch

> **Branch purpose**: This branch runs as a **single-user, local desktop application**. Users launch it on their own machine (Mac or Windows) — the Flask server opens a browser tab automatically and communicates with a **PyBadge colorimeter** over USB HID/serial.

## 2. Critical Rules for AI Coding

### 2.0 Mandatory First Step: Read EASY OKAPI.md

- **BEFORE executing any commands like `ls -R` or `find` to explore the codebase**, you **MUST** read `easyokapi-knowledge/EASY OKAPI.md` first.
- This document holds the summary, architecture, codebase map, and exact roadmap of the project. Prioritizing reading this prevents wasting tokens on excessive directory listings and codebase guessing.

### 2.1 Data Storage — Always Use Local Filesystem

- **All CSV and JSON operations use `os.path`, `open()`, `Path`, `glob`, `shutil`, `pandas`.**
- There is **no** in-memory `USER_DATA` dict, no session-based storage.
- Files are read from and written to the user's local disk directly.
- The current browsed directory is tracked in `file_path.py`'s global `current_directory`, always within `DATA_ROOT` (`data/`).
- Modifications to files (`edit_file`, `delete_file`, `copy_file`) operate directly on the filesystem.

### 2.2 Single-User — No Session Isolation

- There is only one user. No Flask `session` for user differentiation.
- Global variables (`process`, `monitor_thread`, `current_directory`) are shared.
- File locks (`filelock.FileLock`) are used for concurrent access to export files, not for multi-user isolation.

### 2.3 Data Logging — PyBadge Communication

- The application communicates with a physical **PyBadge** (Adafruit) colorimeter via USB.
- **Default transport is CDC (USB serial)**, not HID. `/run_script` spawns **`log_cdc_data.py`** as a subprocess that **owns the single serial port for the whole session**: it connects (`send_command.connect_to_device`), sends `1` / `TIMEOUT:x` / `INTERVAL:x`, waits for the device ACKs, then reads the data stream on the **same** connection. Flask must **not** also open the port — one owner only.
  - **Anti-pattern**: do not open the serial port in the Flask process (e.g. to send commands or "0") while the CDC logger subprocess is running — the OS allows a single owner and the second open will fail.
  - Same `python` interpreter for Mac/Windows (`sys.executable`, or the Windows `venv/Scripts/python.exe`); **no `sudo`/admin** — CDC serial needs no elevated privileges and no `libusbK` driver.
- **HID keyboard is the zero-software fallback only**, triggered by the device's **Left button** (firmware `serial_manager.serial_talking(start_by_host=False)` → `transport="hid"`). The device "types" CSV as keystrokes into whatever text field has focus (e.g. a text editor) — there is **no host-side HID capture script**; the old `log_hid_data.py` / `log_hid_data_pyusb.py` (and the `hidapi`/`pyusb`/`libusbK` stack) have been removed. The host app's automated flow only uses CDC.
- Firmware transport switch lives in `open_colorimeter_firmware/src/serial_manager.py` (`_write()` routes to `usb_cdc.data` for CDC or the HID `layout` for the fallback). The device boot must enable `usb_cdc.data` **and** leave HID keyboard on (`boot_for_CDC.py` does both — `usb_cdc.enable(console=False, data=True)` plus the default HID keyboard). `console=False` is load-bearing, not cosmetic — see §2.28.
- CDC delivers exact bytes, so `log_cdc_data.py` parses **clean text** (`# Measurement:`, `Timestamp,Value:1`) — unlike the HID path, which had to undo keyboard up-casing/modifier-stripping (`3 MEASUREMENT:` etc.).
- Because CDC is a reliable byte stream, the old **missed-read / resend** machinery has been removed entirely (no `max_resend_attempts` setting, no `check_log_for_missed_read`, no resend state). `check_status` reports `running` / `success` (session completed, log has "New session started") / `failure`.
- **Session-end sentinels (device → host):** the firmware ends a host (CDC) session by streaming one of two text sentinels, parsed by `log_cdc_data.py` (`is_end_session` / `is_stopped` → `_finish_session`, which logs the sentinel verbatim):
  - `SESSION TIMEOUT` — the configured timeout elapsed.
  - `SESSION STOPPED` — the user pressed the device's **Left button** mid-session (firmware `serial_manager.serial_talking()` emits it when `transport == "cdc" and not start_by_host`; the host's own `0`-command stop passes `start_by_host=True` and does **not** emit it). Both repos are kept in lockstep — adding/renaming a sentinel means editing **`open_colorimeter_firmware/src/serial_manager.py` on every branch (`main`, `open-plus`, `open-uv`)** and the host parser + `script_monitor.check_log_for_end_reason` together.
  - The reason flows to the UI announcement: `check_log_for_end_reason()` → `check_status` message, mirrored by the `cdc-logging.js` `fetchLogs` regex; the popup reads "Session ended due to timeout." vs "Session stopped manually on the device." **Anti-pattern**: do not hardcode the timeout wording in `resetUIAfterCompletion` — it must use the backend's reason-aware message so whichever poller wins the race shows the correct cause.
- HID logging is **disabled in calibrate mode**.
- The subprocess writes to `log/script_logs.txt`, which is monitored for errors (`script_monitor.check_log_for_errors` / `check_log_for_session_start`).
- The PyBadge VID/PID: `0x239A` / `0x800B` (HID) or `0x8034` (serial)

- **No obfuscation, no minification, no `build.js`, no `npm run build`.**
- There is no `static/dist/` directory.

### 2.6 Data Folder Management

- Users are **restricted to the `data/` directory** (project root). Free filesystem browsing is no longer allowed.
- A **subfolder picker** UI lists immediate subdirectories of `data/` with search and sort by name.
- `src/file_path.py` exports `DATA_ROOT` constant, `validate_in_data_root(path)`, and `get_data_subfolders()`. There is **no mutable `current_directory` state** — the backend is stateless; directory tracking is owned by the frontend.
- **Reserved folder name `root`**: `src/file_path.py` exports `RESERVED_ARCHIVE_FOLDER = "root"` and `is_reserved_data_folder_name(name)` (case-insensitive, trims whitespace). `data/root/` is the staging folder the installers use to hold loose data-root files during the uninstall/reinstall archive cycle (see §2.16), so a user **cannot** create a subfolder called `root`. The check is enforced server-side in `/run_script` (subfolder) and `/rename_data_folder` (new_name), and client-side in `hid-logging.js` (new-folder input) and `navigation.js` (`isReservedDataFolderName`, rename validator). The JS constant `RESERVED_DATA_FOLDER` mirrors the Python constant — keep the two in sync.
- `src/state.py` tracks `data_root_path`, `report_root_path`, `json_root_path` (all auto-created on startup).
- Route `GET /get_data_folders` returns `[{"name": "...", "path": "..."}, ...]`.
- Route `POST /rename_data_folder` (`{path, new_name}`) renames a subfolder in place via `os.rename`. The source `path` must validate inside `data_root` and not be the root itself; `new_name` must be a bare folder name (rejects `..`, `/`, `\`, `\x00`, and any `.`/`_` prefix so the result stays visible in the picker — `get_data_subfolders()` hides those). Returns the new absolute `path` so the frontend can re-point the active directory when the renamed folder was selected. Blocked (`423 LOCKED`) while the HID collection process is running, mirroring `/delete_data_folder`. Frontend: `renameDataFolder(name, path)` in `navigation.js`, triggered by the pencil button on each `.folder-item`.
- Route `POST /browse` is **stateless** (never writes backend state): validates path is within `data_root_path` or `report_root_path`, returns files. Removed routes: `/get_parents`, `/get_children`. **Exception — on-disk ConcenUnit back-fill**: for a path inside the data root it first calls `file.ensure_concen_unit_in_dir()` to insert a `# ConcenUnit: ng/µL` line into legacy CSVs lacking it (idempotent, best-effort; see Rule.md §2.10). This is the only filesystem write `/browse` performs and is confined to the data root.
- Template variables passed from `index()`: `data_root`, `report_root`, `json_root` (replaces `directory`).
- JS constants: `DATA_ROOT`, `REPORT_ROOT`, `JSON_ROOT` (replaces `rootPath`). Defined inline in `index.html` before external scripts are loaded.
- Path delimiter: `\\` on Windows, `/` on Mac/Linux.
- Hidden directories (starting with `.` or `_`) are filtered out.
- **Anti-pattern**: Do **not** restore `get_directory()`, `browse_directory()`, `get_parent_directory()`, or `current_directory` global in `file_path.py` — these have been permanently removed.
- `/run_script` payload uses `subfolder` (folder name only, no slashes) instead of `base_dir`; backend constructs `data/<subfolder>` and creates it if needed.
- Route `POST /move_file` (`filename`, `path`, `dest_path`; form-encoded) moves a CSV data file between data subfolders. Both `path` and `dest_path` must validate inside `data_root`; `filename` must be a bare name (no `/`, `\`, `..`); same-folder moves are rejected; a name clash in the destination is auto-incremented via `get_next_filename` so a move **never** clobbers an existing file. Blocked (`423 LOCKED`) while the HID process runs. Frontend: `moveFile()` in `data-handling.js` (Move button `#move-file-btn`, enabled/disabled alongside `#copy-file-btn`) shows a SweetAlert2 folder-select dialog (data root + subfolders, excluding the current folder). CSV-only: it bails in `report` mode.
- **Manual creation — no reading run required.** A user can make data folders and empty CSV files without a connected colorimeter:
  - Route `POST /create_data_folder` (`{name}`) creates an empty subfolder under `DATA_ROOT`. Same name rules as `/rename_data_folder` (bare visible name; no `..`/`/`/`\`/`\x00`, no `.`/`_` prefix, not the reserved `root`); rejects an existing name (`409`); blocked (`423 LOCKED`) while the logger process runs. Frontend: `createDataFolder()` in `navigation.js` (**＋ New folder** buttons beside Refresh in both folder pickers) → prompt → refresh.
  - Route `POST /create_csv_file` (`{mode, cal_mode?, filename, path?, num_sources?, num_lines?, concenUnit?}`) writes a **template CSV** with the mode's correct metadata block + header row and `num_lines` blank placeholder data rows (default 0 = header only), so it opens straight in the file editor for manual entry. Placeholder rows are written **editor-valid** (timeseries: an incrementing `Timestamp` with empty value cells, e.g. `0,,`; calibration: all `NONE`) so a later editor save doesn't fail the `_SCHEMA_VALIDATORS` regex. `kinetics`/`point` → a timeseries file (`# Measurement/Unit/Concentration/ConcenUnit` + `Timestamp,Value:1..N`); `calibrate` → a calibration table for `cal_mode` (reuses `write_metadata`/`write_headers`, so `kinetics` → `Concentration,maxRate,Slope,Sat,Time To Sat`, `point` → `Concentration,Value,TimePoint`). `path` must validate inside `DATA_ROOT`; `filename` is a bare name (an optional `.csv` is stripped); a name clash is auto-incremented via `get_next_filename` so it **never** clobbers an existing file; blocked (`423 LOCKED`) while running. Frontend: `createCsvFile()` in `data-handling.js` (**＋ New CSV** button in File Selection) reads the active mode / cal sub-mode (`#cal-mode-select`) / `AppState.numSources`, then refreshes the file table. **Anti-pattern**: do not emit calibrate CSV headers by hand — reuse `write_metadata`/`write_headers` so a new file stays byte-identical to the export path.
- Route `POST /export_to_report` copies a measurement file **out of the data tree into a report subject** (`report/<subject>/`). The source (`file_path`) must therefore be confined to the **DATA root** (`validate_in_data_root` / `DATA_ROOT`), **not** the report root — relative paths resolve against `DATA_ROOT`; a source outside it is rejected `403`. **Anti-pattern**: do not anchor this source check on `state.report_root_path` — the frontend (`exportToReport()` in `report.js`) sends a path under `data/`, so anchoring on the report root makes every export 403 (this regressed once and only surfaced visibly after a data-folder relocation).

- `POST /shutdown` terminates the Flask server process after a 5-second delay.
- Renders `goodbye.html` before termination.
- `cleanup()` in `browser_mgt.py` runs via `atexit`: kills subprocess, closes port.

- Unlike the `online` branch, there is **no Flask-SocketIO, no eventlet**.
- All communication is standard HTTP request/response or AJAX (`$.ajax` / `fetch`).
- After file modifications, the frontend must **manually refresh** data by re-fetching from the API.

### 2.10 CSV Data Format

CSV files follow this structure:
```
# Measurement: Absorbance
# MeasUnit: abs
# TimeUnit: s
# MeasMode: kinetics
Timestamp,Value:1,Value:2,...
0,0.123,0.456,...
```
- Metadata lines start with `#` and contain `Key: Value` pairs.
- Required metadata: `Measurement`, `MeasUnit`, `TimeUnit`, `MeasMode`.
- Data header starts with `Timestamp` followed by `Value:n` columns (for measurement data).
- Calibration CSVs use: `Concentration,maxRate,Slope,Sat,Time To Sat` (kinetics) or `Concentration,Value,TimePoint` (point).
- Multi-source files have multiple `Value:` columns (`Value:1`, `Value:2`, etc.).
- **A value cell is a number or one of three device tokens — `OVFL`, `NONE`, `INF`** (`src/sentinels.py`, the single source of truth; firmware `serial_manager._fmt`). `OVFL` = sensor saturated; `NONE` = nothing measured yet (a blank-needing measurement on a device that is not blanked — a channel change resets the blanks); `INF` = a fully attenuated channel: zero counts through the cuvette, so the absorbance is infinite. Firmware branches predating the token write Python's own `inf`, so every reader accepts that spelling too. **Rows are validated whole**: a value the pattern does not recognize drops the entire row, healthy channels included — one dark cuvette used to empty a whole session file, because the device streamed `inf` and no pattern matched it. The token list therefore lives in **one** place per language and is referenced, never re-typed: `sentinels.TOKEN_PATTERN` (`log_cdc_data.data_pattern`, `_SCHEMA_VALIDATORS` in `file_routes.py`) and `MEAS_SENTINELS` / `measNumber` in `short-hands.js` (used by `calculate.js`, `report.js`, `cdc-logging.js`; the `edit-file.js` `patternSets` mirror the backend regex). Covered by `tests/test_sentinels.py`. **Anti-pattern**: do not coerce a value cell with a bare `float()` / `Number()` — `float("INF")` returns an *infinity* (unlike `float("OVFL")`, which raises), which then poisons fits, JSON (`Infinity` is not valid JSON) and Excel cells. Filter through `sentinels.to_number` / `measNumber` first: they reject the tokens **and** any non-finite result.
- **Saturation (Sat) requires a confirmed plateau**: `math_ops.calculate_kinetics_quantities` reports `saturationValue`/`timeToSaturation` only when a real plateau is found — the segment after the linear region must hold `>= max(3, window_size // 2)` points **and** have its own linear slope `<= SAT_FLAT_FRACTION` (0.10) of `max_rate` (`_tail_is_flat`). If the trace was interrupted while still rising (tail slope near `max_rate`), the tail is too short, or no linear region exists, Sat is `"--"` — never a median of still-rising or arbitrary data. Max rate + linear region are still reported in those cases. The JS Sat display keys off `saturationValue === "--"` (`data-display.js`), not `timeToSaturation !== null`. Covered by `test_calc_kinetics_*` in `tests/test_math_ops.py`. **Anti-pattern**: do not emit a Sat number without the flatness gate.
- **Concentration unit (`# ConcenUnit`)**: the unit a concentration is expressed in — the `# Concentration:` value of a raw timeseries file, or the `Concentration` column of a calibration file. One of **`ng/µL` (micro sign), `nM`, or `%`** — exactly these three (`CONCEN_UNITS` in `src/file_path.py`, the single source of truth, injected into the page as the `CONCEN_UNITS` JS const + validated in `user_settings._VALID_CONCEN_UNITS`); a **label only** — switching units never converts the recorded numbers. Constants + the `get_concen_unit(meta)` fallback helper live in `src/file_path.py` (`CONCEN_UNITS`, `DEFAULT_CONCEN_UNIT`). The user's preferred default for **new exports** is the `default_concentration_unit` user setting; the frontend `#concen-unit` dropdown (Data Display section, options rendered from `concen_units`) reflects the loaded file's unit and selects the unit for the next calibration export (`getMetaConcenUnit` in `data-display.js`). In the **Edit File** metadata table, `ConcenUnit` is edited via a **`<select>` of `CONCEN_UNITS`** (not free text) so an invalid unit can't be typed — `collectTableContent` reads the select's value; keep the JS `CONCEN_UNITS` injection in lockstep with the Python list.
  - **Backward compatibility — absent ⇒ ng/µL**: older files predate this line. When `ConcenUnit` is missing it is assumed to be `ng/µL`. The line is **back-filled onto disk when a data folder is selected**: `POST /browse` (data-root paths only) calls `file.ensure_concen_unit_in_dir()`, which inserts `# ConcenUnit: ng/µL` into the metadata block of every recognized CSV (timeseries / kinetics-cal / point-cal) lacking it. Idempotent, best-effort, and it **always writes `ng/µL`** (never the user's preferred default) so it can never mislabel existing data.
  - **Export consistency guard (required)**: `export_data.is_metadata_consistent()` compares the target file's `ConcenUnit` (defaulting an absent one to `ng/µL`) against the export's unit — you **cannot** append `nM` rows to a file recorded as `ng/µL`, or vice versa. `/export_data` returns a clear `Concentration unit mismatch` error; pick a different file or unit. `write_metadata()` emits the `# ConcenUnit:` line for new calibration files.
  - **Anti-pattern — single-entry export fields must stay in the `@validate_json` schema**: `/export_data` supports two payload shapes — a **batch** (`entries: [...]`, used when >1 source is exported) and a **single entry** (the row's `con`/`maxrate`/`slope`/`sat`/`timeSat`/`estValue`/`timePoint` at the top level, used for exactly one source). The single-entry path reads those values from `validated_data`, but `@validate_json` **drops any key not declared in its schema**, so every one of those fields must remain declared (permissive `((str,int,float),'NONE',False)`) or a one-source export silently writes a row of all `NONE` (the batch path is unaffected because list items pass through untouched). Covered by `test_export_data_single_source_*`.
  - **CDC mandate**: a host-initiated CDC session must send all **four** metadata lines (`Measurement`, `Unit`, `Concentration`, `ConcenUnit`) before the data header — `log_cdc_data.handle_main_header()` gates on `len(metadata) == 4`. The firmware (`open_colorimeter_firmware`, separate repo) is updated in lockstep to always emit `# ConcenUnit:`; an old 3-line firmware session is rejected by design. **Anti-pattern**: do not relax the gate back to 3 or migrate the *live* file from the `#concen-unit` dropdown (legacy files are migrated only via `/browse`).
- **None-able metadata fields edited via a "None" checkbox**: the **measurement unit** (`# Unit` timeseries / `# MeasUnit` calibration) and the **concentration value** (`# Concentration`) may legitimately be *None* — a measurement can be unitless and a raw timeseries needn't record a concentration. In the **Edit File** metadata table (`edit-file.js`) and in the graphic JSON editor's `meas_unit` field, each of these renders a **"None" checkbox + text input**: ticking the box locks the input and writes the **`NONE`** sentinel; unticking it re-enables free-text entry. On load the box starts ticked when the stored value is a *None-variant* — blank or `NONE` (any case), mirroring `src/file.py::_norm_identity_value` (the JS gate is `isNoneMetaValue` in `edit-file.js`). The reader (`preConfirm` for the table, `setValueByPath` for the JSON cell) emits `NONE` when boxed **or** when the input is left empty, so the file stays format-valid (the metadata regexes require a non-empty `.+` after the colon and accept `NONE`; server-side `_norm_identity_value` normalizes it back to a wildcard). **`ConcenUnit` is deliberately NOT None-able** — a concentration always has a unit, so it stays a constrained `<select>` (see the ConcenUnit bullet above). New user-facing label `metadata.none` lives in all six `ui_translations/*.json`; the dialog is otherwise hardcoded English so the label is resolved inline via `t('metadata.none','None')`, not `data-i18n` (which only applies at page load). **Anti-pattern**: do not write an empty value for these fields — always emit the `NONE` sentinel so the CDC 4-line gate and the editor schema validators still pass.
- **Excel formula export mirrors the JSON coefficient export.** `/export_cal_excel_formula` (`src/excel_formula.py`) is the sibling of `/export_cal_coefs`: it turns the fitted standard-curve coefficients into ready-to-paste Excel formulas instead of a JSON file. It **reuses the identical coefficient pipeline** — `extractAnalysisCoefficients(coef_content, threshold, algo)` → `processJSONCoef(cal_params, …, algo)` — then `formulas_from_content` walks that structure (top-level `fit_coef` = single source; per-source keys = multi-source) into one `quantity → concentration` formula each. The formula math must stay in lockstep with `math_ops.py`'s model functions (linear `a*x+b`, polynomial `a*x^2+b*x+c`, logarithmic `a*ln(x+b)+c`, exponential `a*e^(b*x)+c`, Michaelis-Menten `(Km*x)/(VMax-x)`). Every coefficient is **wrapped in parentheses** so a negative value is valid Excel (`+(-3)`, never `+-3`); a below-threshold / failed fit yields a `null` formula (not an error). The `cell` argument is validated against `_CELL_RE` (an A1-style ref). **Anti-pattern**: do not re-derive the coefficients differently here — reuse `processJSONCoef` so the formula matches what the JSON export records; do not build formulas by string-concatenating bare signed numbers (parenthesise).
- **CSV↔JSON identity matching (calibration pairing)**: a measurement CSV (kinetics/point) is paired with a **calibration JSON** to derive concentration; the pair must share the same **Measurement + Unit + ConcenUnit**.
  - **JSON identity**: calibration JSONs store `for_meas` (Measurement), `meas_unit`, `concen_unit` (written by `/export_cal_coefs`; the JS caller sends `measUnit`=`getMetaUnit(metaData)` + `concenUnit`=`#concen-unit`). These keys are plain JSON, so they are editable in the Edit-File **text** editor and shown in the JSON Fit-Information panel. In the Edit-File **graphic** editor (the default for the JSON table), `concen_unit` is rendered as a **`<select>` of `CONCEN_UNITS`** via the `configs` map in `edit-file.js` (the same mechanism as `fit_type`); a legacy value outside the catalog is preserved as an extra option. `meas_unit` stays free text (measurement units aren't a fixed catalog) but gains a **"None" checkbox** that locks the field and stores the `NONE` sentinel — see the None-able-metadata bullet in §2.10. Keep the `CONCEN_UNITS` injection in lockstep with the Python list.
    - **Legacy back-fill**: a JSON predating this feature has neither key. `file.ensure_cal_units_in_dir()` writes the defaults onto disk for every non-`*.meta.json` calibration JSON missing them — `meas_unit` → `"NONE"`, `concen_unit` → `ng/µL` — as the list is fetched (`/get_json_cal`, and the index kinetics first paint). Idempotent, best-effort, mirroring the CSV `ensure_concen_unit_in_dir`. The `"NONE"` placeholder is **normalized back to a wildcard** (`None`) by `build_json_identity` / `_norm_identity_value` (Python) and `_normIdent` (`navigation.js`), so a back-filled curve still pairs with any measurement unit while keeping ConcenUnit enforced.
  - **Identity surfaced per file**: `file.build_csv_identity()` / `build_json_identity()` return `{name: {measurement, unit, concen_unit}}` (CSV `unit` = `# Unit` for timeseries / `# MeasUnit` for calibration, mirroring `getMetaUnit`; concen defaults ng/µL). `/browse` returns `files_identity`, `/get_json_cal` returns `files_identity`, and the index route injects `FILE_IDENTITY` / `CAL_JSON_IDENTITY`. Both tables show an inline `Measurement·Unit·ConcenUnit` badge (`.file-identity`), rendered in **both** the Jinja first paint and `navigation.js` (`_identityBadge`) — keep in lockstep (Rule §2.21).
  - **Match rule** (`identityMatch` in `navigation.js`): Measurement and Unit are **wildcards when absent on either side** (legacy JSONs stay usable); ConcenUnit is **always enforced** (absent ⇒ ng/µL); the **`axis`** (turn/time) is enforced when present on both sides (a Turn data file pairs only with a turn calibration and a Timestamp file only with a time calibration — Rule §2.27; absent on either side ⇒ wildcard, so kinetics/legacy curves stay usable). `build_csv_identity`/`build_json_identity` and the JS `csvIdentityFromMeta`/`jsonIdentityFromContent` therefore also carry `axis`. Applies in **kinetics/point** mode only.
  - **UX**: when a counterpart is selected, non-matching rows in the other table keep their badge but their **Select button is disabled** with a reason tooltip (`_selectDisableAttrs`); selecting/deselecting re-renders the counterpart table to refresh disabling. `selectFile` also raises an explicit `Swal` mismatch error as a backstop if a disabled button is bypassed. **Anti-pattern**: do not enforce a missing Measurement/Unit as a hard mismatch (it would orphan legacy JSONs — they are wildcards); do not skip the `selectFile` backstop (the disabled button alone is not authoritative).
  - **Re-validate on edit** (`revalidateActivePairing` in `data-handling.js`): the selection-time backstops only fire when a file is *picked*. Editing a file's metadata while a CSV **and** a calibration JSON are both selected can misalign a previously-matched pair without any re-selection, so the now-mismatched curve would keep being applied. After a successful `/edit_file` the handler reloads the edited file, refreshes the identity maps (`updateDirectory` / `updateJSONTable`), then calls `revalidateActivePairing()`, which compares the **authoritative loaded data** — `csvIdentityFromMeta(AppState.metaData)` vs `jsonIdentityFromContent(AppState.currentJSONcontent)`, not the table maps (which may lag) — and on a clash **unpairs the curve** (`deselectFile('#json-table')`, clearing any derived concentration) with a warning, suppressing the routine success toast. **Anti-pattern**: do not re-validate against `AppState.fileIdentity`/`jsonIdentity` straight after an edit (stale until refetched); use the loaded `metaData`/`currentJSONcontent`.
  - **Identity-aware search** (`filterTable` in `navigation.js`): the CSV (`#file-search`) and calibration-JSON (`#json-search`) search boxes use **space-separated positional filters**, all AND-ed (set intersection): position 1 = **name**, 2 = **measurement**, 3 = **unit**, 4 = **ConcenUnit**. `parseSearchQuery` tokenizes the query (quoted values allowed for spaces, e.g. `std "Total Protein" AU nM`); a bare `-` or empty `""` **skips** that position, and extra tokens past the fourth are ignored. `_identityFieldMatch` tests each active filter as a **case-insensitive substring** against the row's identity from `AppState.fileIdentity` / `jsonIdentity` (absent ConcenUnit defaults to `ng/µL`; absent Measurement/Unit match only an unset filter, so a measurement filter hides files that don't declare it). The name cell holds the identity badge, so the badge text is stripped before name matching and identity is read from `AppState`, never scraped from the DOM. Field filters are **ignored** for the report-subject folder listing (which reuses `#file-table` without identity). **Anti-pattern**: do not parse the badge text out of the cell for filtering — look identity up from `AppState`.
- **Point-mode reference unit**: the "Set reference point to export" input (`#exp-json-time-value`) is entered in the currently-selected `#time-unit`; its label and value rescale whenever `#time-unit` changes (`refreshExpTimeValueForUnit` in `init.js`). Estimates use the selected unit, but **exports always convert the reference point to minutes** (`generatePointData` in `data-handling.js`) so calibration files stay in minutes (`TimeUnit: minute`).

### 2.14 Event Logging — User Interaction Tracing

- Logs are stored under `log/events/YYYY-MM-DD/HH-MM-SS.jsonl`: one date folder per calendar day, one JSONL file per app launch within that day (name = session start time).
- Module-level `_SESSION_DATE` / `_SESSION_START` constants are set once at import time so all events in one process go to the same file.
- Each entry: `{"ts": "YYYY-MM-DDTHH:MM:SS", "type": "...", "action": "...", "details": {...}}`.
- `append(type, action, details=None)` — writes one JSONL line to the current session file.
- `read_all()` — reads all events across all date folders and sessions, oldest first.
- `cleanup_old_logs()` — retention N keeps exactly the N most recent calendar days (today counts as day 1; N=1 → only today's folder); called on every session start (index route) and after every successful `POST /settings`, so lowering the retention prunes immediately.
- Routes: `GET /event_log` returns all events; `POST /event_log` (`{type, action, details?}`) appends one entry.
- Frontend: `logEvent(type, action, details)` in `static/script/event-tracker.js` (loaded first) — fire-and-forget `fetch`, never blocks the UI.
- Tracked events: `session:start` (page load), `mode:switch`, `file:select/delete/copy`, `data:display`, `hardware:start/stop`, `report:generate`, `settings:save`.
- **Anti-pattern**: Do not `await` log calls or show errors to the user when logging fails — logging is always best-effort.

### 2.13 AI Assistant — Groq Cloud LLM

- The AI assistant uses **Groq** (cloud API) — no local model server required.
- Desktop instances authenticate via `activation.json` (permanent license token, **hardware-locked** — see §2.17) and proxy requests through the online Heroku server, sending their `hwid` with each proxy call.
- **AI entitlement is split by build type** (`_get_api_mode()` / `_dev_key()` in `src/routes/ai_routes.py`): an **installed/frozen build** (`state.IS_FROZEN`) requires a valid activation token — the `.env` `GROQ_API_KEY` bypass is **ignored** there, so a token is genuinely mandatory and dropping a `.env` beside the binary cannot unlock the AI. A **source run** (`python main.py` / `setup-3-run.command`) needs no token: `GROQ_API_KEY` in `.env` enables `dev` mode (and the transient proxy-error fallback) directly. The frozen rule lives only in `_dev_key()` — both mode selection and the proxy fallback consult it, so do not re-derive it elsewhere. **Anti-pattern**: never honour a local Groq key in a frozen build.
- AI-assistant preferences live in **`user_settings.json`** via `src/user_settings.py` (`ui_language`, `ai_feedback_enabled`) — **not** in a separate `ai_settings.json`. `user_settings.py` also owns **`SUPPORTED_LANGUAGES`**, the single source of truth for the six UI/AI-chat languages, imported by `i18n.py` and `routes/ai_routes.py`. The old `src/ai_settings.py` (its `load()`/`save()`/`ai_settings.json` persistence was dead — nothing wrote or read the file — and it held only that one constant) was **deleted**; the constant moved into `user_settings.py`. **Anti-pattern**: do not recreate `ai_settings.py` or `ai_settings.json` — add per-user AI prefs to `user_settings.py`. (Legacy `ai_settings.json` files stay in `update_service._PRESERVE` only so an old install's copy is never clobbered on update.)
- All chat calls go through `src/ai_assistant.py` using the `requests` library.
- The AI blueprint is `ai_bp` in `src/routes/ai_routes.py`, mounted at `/ai/*`.
- Supported languages: `en`, `vi`, `zh`, `fr`, `ja`, `ru`. System prompts for all 6 are embedded in `ai_assistant.py`.
- `AI.activeLang` in `ai-chat.js` tracks the currently active language, selected via the header button; chat requests send `AI.activeLang` (chat language is independent of `ui_language`).
- **Server-side rate limit + payload caps are the authoritative guard on `/ai/chat`** (`routes/ai_routes.py`). The browser limiter (15/60s in `ai-chat.js`) is UX only — it is bypassable and every accepted call spends a paid Groq/proxy request. The route trims the forwarded history to the newest `_MAX_MESSAGES` turns, rejects an over-cap payload with **413** (`_MAX_MSG_CHARS` per message, `_MAX_TOTAL_CHARS` summed), and refuses more than `_RATE_MAX` requests per `_RATE_WINDOW`s with **429** + a `Retry-After` header — all **before** any upstream call, and the size gate runs before the limiter records a hit. One process-wide sliding window (deque under a lock) suffices because the app is single-user. `/ai/match` caps its query to `_MAX_MSG_CHARS` (the local difflib matcher). The 413/429 messages are localized via `_localized()`. **Anti-pattern**: do not rely on the client limiter alone, and do not call the proxy/Groq before the size + rate checks.
- MCP tools (`TOOLS` list in `ai_assistant.py`) give the LLM access to live app state: file list, CSV content, calibration JSON, hardware status, and built-in help docs.
- **LLM-supplied file paths are untrusted and must be confined to their root.** A tool argument that names a file (`read_csv_file` → `validate_in_data_root`; `read_calibration_file` → `validate_in_json_root` + `os.path.basename` on the filename + `mode` pinned to `{kinetics, point}`) is chosen by the model, so it is an injection surface. `json/` sits directly inside `state.script_dir` next to `activation.json` (the license token), `.env`, and `user_settings.json`; an unvalidated `..` in the filename/mode reaches those and returns them to the model/proxy. **Anti-pattern**: do not `os.path.join(root, mode, filename)` a tool-supplied path without a root check — mirror `read_csv_file`, which always did.
- **Streaming**: `chat_stream` (the dev/local-Groq path) uses `_groq_chat_stream`, which sets `stream=True` and yields content deltas live as `{"type":"chunk"}` SSE events (the frontend renders them token-by-token). Tool calls are reassembled from their streamed argument fragments (accumulated per `tool_call.index`) so the tool-calling loop is unchanged. The guide-launched confirmation is emitted only when the model streamed no prose that turn (`streamed_any`), to avoid duplicating its message. The production path (`proxy_chat_stream`) relays whatever the online server streams.
- **Deterministic no-LLM turns run once, for BOTH paths, in the route.** Greeting (`_is_greeting`→`_GREETING_RESPONSE`), out-of-scope refusal (`_is_out_of_scope`→`_OUT_OF_SCOPE`), and the report quick/full clarification flow are produced by `ai_assistant.deterministic_events(messages, language, ui_context)` — a pure function returning a list of SSE event dicts, or `None` to fall through to the model. `/ai/chat` calls it **after the rate-limit/payload gate but before dispatching** to either `proxy_chat_stream` or `chat_stream`, so an activated (proxy) user gets exactly the source-run behaviour instead of depending on the `online` server to re-implement it — and no upstream call is spent on a turn the model never needed. `chat_stream` also calls `deterministic_events` first (idempotent) so it stays correct when invoked directly (dev fallback, tests). The clarify flow's **quick** branch reuses the **`generate_report_dialog`** guide (via `_guide_example_by_id` + `_format_fewshot_hint(..., steps_only=True)`, which applies its `requires_mode`/`requires_data_loaded` prefixes) — the *same* walkthrough the `/report` slash command's Quick choice launches — so both entry points step INTO the Report Details Swal identically; there is no separate inline `_QUICK_REPORT_STEPS` list any more. **Anti-pattern**: do not re-inline greeting/out-of-scope/report-clarify branches into `chat_stream` only — that path is skipped for activated users, so the behaviour would silently diverge; keep them in `deterministic_events` so the route applies them to both.
- **Truncation is flagged, not silent; an empty reply is retried, not dead-ended.** `_groq_chat_stream` records `finish_reason` on its `("result", …)`. When a plain-text answer stops for `"length"` (hit `_MAX_COMPLETION_TOKENS`), `chat_stream` appends the localized `_TRUNCATION_NOTICE` so a rare over-budget reply reads as continuable rather than cut off mid-word. When the model returns **no prose and no tool call**, `chat_stream` retries the turn **once with tools disabled** (`empty_retry_used` latch — a tool-less ask reliably yields text) before giving up quietly (the client shows its own `_EMPTY_REPLY` fallback). **Mirror both on the `online` proxy**, which controls its own `max_tokens` and loop. **Anti-pattern**: do not return silently on an empty completion, and do not let a `length` cut-off reach the user unlabelled.
- **Tool schemas carry NO `enum` constraint — validate permissively in `_run_tool` instead.** Groq validates tool-call arguments against the JSON schema server-side, so an `enum` turns any out-of-set value the model picks into a hard 400 (`tool_use_failed`) *before* `_run_tool` runs — the single biggest source of "failed to call a function" on the small Llama models (e.g. `get_help_topic` with `topic="about"` for "what is this software about"). The valid values stay in each parameter's `description` (so the model still knows them), but enforcement moves into `_run_tool`, which normalizes/falls back: unknown `topic` → nearest key or the `overview` doc; bad `workflow` → `general`; out-of-range `position` → `bottom`; `mode` must still be `kinetics`/`point` (also a path-safety check). **Anti-pattern**: do not add `enum` (or other hard `required`/format constraints the model can violate) to a tool schema — describe the allowed values and validate in `_run_tool`. Completion budget is `_MAX_COMPLETION_TOKENS` (2048, up from 1024/500) so neither a long tool-call argument list nor a full multi-mode coefficient explanation is truncated into malformed JSON or a mid-sentence cut-off. The system prompts also carry an ANSWER-DIRECTLY rule telling the model to answer general/conceptual questions from its own knowledge and reserve tools for live data or an explicit guide — cutting redundant tool calls. **Mirror all of this on the `online` proxy server**, which has its own TOOLS/prompt copy; the desktop dev path is fixed here but the activated build calls the proxy.
- **Invalid tool call is recoverable, not an error to show the user.** Small Llama models sometimes emit a tool call Groq rejects with a **400** (`tool_use_failed` / "did not match schema" / "Failed to call a function") — typically on short, ambiguous prompts ("what is this software about" → `get_help_topic` with an out-of-enum `topic`). `_map_groq_error` tags these via `_TOOL_FAILURE_MARKERS` as the stable code `tool_call_failed`; `chat_stream` then **retries the same turn once with tools disabled** (`active_tools=None`, `tools_enabled` latch) so the model answers in plain text instead of leaking `failed_generation`. The frontend (`ai-chat.js`) renders the `tool_call_failed` code — **and any raw Groq tool-failure string** from the proxy path, matched by `_isToolFailure()` — as the friendly localized `_TOOL_FALLBACK` line. The dev path truly recovers (retry); the proxy path can only render nicely here — the same retry belongs on the `online` server. **Anti-pattern**: do not surface a raw `tool_use_failed`/`failed_generation` string to the user, and do not treat an invalid tool call as fatal without the tools-off retry.
- **Report quick/full clarification is language-independent.** `_needs_report_clarification` recognises "report" in all six languages (`_REPORT_WORDS`) and `_get_pending_report_type` identifies the prior clarify turn by **exact match** against `_REPORT_CLARIFY_PROMPTS.values()` (`_is_report_clarify_prompt`), not by substring-matching the English phrase "quick report"/"full report" — the localized prompts never contain those, so the old check silently failed for vi/zh/fr/ja/ru. Quick/full answers are matched against the multilingual `_QUICK_KWS`/`_FULL_KWS` sets. **Anti-pattern**: do not gate this flow on English substrings of a string that is emitted localized.
- **A mode-specific guide uses a soft `requires_mode`, not a hard `conditions.mode`, unless it has a per-mode variant.** `conditions.mode` in `guide_training.json` **excludes** a guide from matching outside that mode (`_match_guide_example` does `continue`) — correct only when a competing variant fires instead (e.g. `concentration_calc_kinetics` vs `_point`). For a feature that exists in exactly one mode with **no** variant (e.g. Save Linearity Range, kinetics-only), a hard gate makes the guide vanish outside that mode, so a strong query ("save linearity range") matches nothing locally and **falls through to the LLM**, which lands on an unrelated screen (`#log-cdc-data`). Use `requires_mode` instead: the guide stays matchable in every mode, and `_format_fewshot_hint` / `ai-chat.js` `_runGuideById` prepend a localized `_MODE_SWITCH_STEP` (`#meas-mode-section`, mode name interpolated as-is) — the same corrective-prepend pattern as `requires_data_loaded` → `_FILE_SELECT_STEP` (switch-mode is prepended last so it lands ahead of file-select). `requires_mode` may be a **single mode string OR a list** of acceptable modes (`_requires_mode_satisfied`); a list is joined with ` / ` in the switch step (language-neutral, mode names stay English — e.g. "kinetics / point"). `edit_calibration_curve` uses `["kinetics","point"]` because the Select-Coefficients JSON panel (`#cal-json-sel-section`) is shown only in those modes. **Anti-patterns**: do not hard-gate a variant-less mode-specific guide (it disappears → LLM fall-through); keep `requires_mode` (str or list) and `_MODE_SWITCH_STEP` in lockstep across `ai_assistant.py` and `ai-chat.js`.
- **Editing a saved calibration curve is its own guide, separate from editing a data CSV.** `edit_calibration_curve` (queries: edit/modify/change × calibration/standard curve/coefficients/json) points its opener at `#cal-json-sel-section` (the "Select Coefficients" panel, expands `json-sel-collapse`) → same editor dialog steps as `edit_file`; `edit_file` (data CSV) points at `#file-selection`. They must not overlap query keywords, or the CSV guide would capture calibration edits (and vice-versa). In **calibrate mode** "modify the calibration curve" intentionally routes to `select_regression` (you change a curve there by adjusting the regression fit), not to the edit guide — that's correct, not a miss. **CJK caveat**: a Chinese/Japanese calibration-edit phrase (`修改校准曲线`, `校正曲線を編集`) can tie/lose to `nav_calibrate_mode` (whose `mode_not:calibrate` gives +1) because CJK phrases get no multi-word specificity bonus (they have no spaces, so `_score_keyword`'s exact-phrase branch scores a flat 1.0 while English "modify calibration curve" scores 2.6). The fix is to enumerate enough distinct matching sub-phrases in the zh/ja overlay `queries` (noun `校正曲線` + verb phrase `曲線を編集` + full `校正曲線を編集`) so their **sum** clears the boosted nav score — verify positives win AND make/create/what-is negatives still don't hit the edit guide. **Anti-pattern**: do not add a bare calibration-curve NOUN as the only new keyword (it ties nav and loses by list order) — add the noun *and* verb-phrase fragments so the sum wins.
- **Guide-step targets must use `data-hint`, not `title`.** `tooltip.js` replaces native `title=` with a `data-hint` attribute, so a control that shows a hover hint has **no** `title` in the DOM — a `button[title="…"]` guide target spotlights nothing (the engine polls 3s then silently skips). Author such targets as `button[data-hint="…"]` (matching `user-guide.js`). This bit `save_linearity_range` step 2. **Anti-pattern**: do not target a hinted control by `[title=…]` — use `[data-hint=…]`.
- **Guide steps can point INTO a SweetAlert2 dialog.** A *dialog step* is one whose target is inside an open Swal — detected by `UserGuide._isSwalStep(step, element)`: an explicit `dialogStep: true` author flag, OR the resolved `element.closest('.swal2-container')` at runtime, OR a selector matching `/swal2|#swal-/` (covers SweetAlert2's own `.swal2-*` classes **and** this app's in-dialog IDs like `#swal-input-filename`, `#swal-ui-language`, which do *not* contain "swal2"). Set `dialogStep: true` when the in-dialog target's selector doesn't advertise it — e.g. the file editor's `#toggle-mode` view-switcher button — so the step is treated as a dialog step even before its element resolves (needed for `_advancePastDialogRun` to skip the run on close). SweetAlert2's `.swal2-container` sits at `z-index: 2147483000` — ~2.1 billion above the guide's normal `~10000` layer — so `positionSpotlight` lifts the **spotlight** (`2147483646`) and **tooltip** (`2147483647`) above it and swaps the full-page dark curtain for a bright ring (`.user-guide-spotlight-swal` — the pulse keyframes re-apply the curtain, so the class also `animation: none`s them); the **overlay stays low (`9998`)** so Swal's own backdrop does the dimming (elevating it would darken the dialog).
  - **Advance / close.** A dialog step attaches `_watchSwalClose`, which polls `document.body.contains(element)` on the specific found element (a follow-up "success" toast is a different element, so it doesn't falsely keep the step alive). `attachInteractionHandler` early-returns for dialog steps so the normal click/blur handler can't double-advance. **Multiple dialog steps can share one open dialog** (e.g. App Settings: change language → Save): the user walks them with **Next** (they are `skipInteraction`), and on close `_advancePastDialogRun` **skips the whole contiguous dialog run** (`_skipDialogRun`) and resumes at the next non-dialog step (or stops) — so cancelling/closing from ANY step in the run never strands the guide polling for vanished elements.
  - **Chained dialogs (`chainsDialog`).** When confirming one dialog opens ANOTHER (e.g. merge's "Select Files to Merge" → **Next** → "Merge CSV Files", opened synchronously in SweetAlert2's `.then()`), flag the step whose confirm triggers the transition with `chainsDialog: true`. On its close, `_advancePastDialogRun` calls `_awaitChainedDialog` — polls up to ~1.8s for the new `.swal2-popup` to mount (SweetAlert2 resolves `.then()` only after the close animation, so the next dialog lands a beat later), then advances ONE step into it; if none appears (user dismissed) it falls back to `_skipDialogRun`. Only the flagged step waits — every other dialog step skips its run immediately on close, so a plain cancel stays snappy. `chainsDialog` is carried through `startCustomSteps`.
  - **The dialog spotlight is click-through.** The ring sits ABOVE the dialog (z `2147483646`), so `positionSpotlight` sets its `pointer-events: none` — otherwise it would swallow clicks on the very button it highlights (Save/Merge/confirm). `.active` CSS defaults the spotlight to `pointer-events: auto`, so this inline override is required (and `stop()` clears it).
  - **`awaitSwalOpen` + `expand` for "pick any file" openers.** A per-row action (edit a file: every row has its own ✏️ Edit) must NOT force one specific button — forcing it robs the user of choosing, and because the overlay closes on any off-spotlight click, clicking a *different* row would close the guide. Instead the opener step sets `awaitSwalOpen: true`: it highlights the panel with the **bright ring** (no dark curtain) and **removes the full-screen overlay entirely** (`overlay.classList.remove('active')` in `setupStepWithElement`, re-added for every other step) so nothing can catch clicks — `pointer-events: none` alone proved unreliable because `positionSpotlight` early-returns for a zero-size target and never applied it. `_watchSwalOpen` advances the moment any dialog opens — so the user freely clicks Edit on any file (data or calibration JSON). `expand: ['file-sel-collapse','json-sel-collapse']` opens the relevant `section-collapse` lists first (`_ensureAncestorExpanded` only expands *ancestors* of the target; these lists are *descendants* of the highlighted panel). Both `expand` and `awaitSwalOpen` must be carried through `startCustomSteps` (which rebuilds each step) and survive `_localizeSteps` (`{...s}` spread). `/edit` (`_runEditFileGuide` → `[_EDIT_PANEL_STEP (awaitSwalOpen), _EDIT_DIALOG_STEP]`) is the reference. **Anti-pattern**: do not target one specific per-row control (`#table button:first`) for a "do X to any row" opener — highlight the panel and use `awaitSwalOpen`.
  - **Reference flows.** `ai-chat.js` slash-command-only builder: `/save-range` (`#save-range-btn` → `.swal2-input`) builds localized `[trigger, …dialog]` steps and calls `_launchCustomSteps`; the trigger step is interactive (opens the dialog), dialog steps are `skipInteraction`. **`merge_files`** is a full `guide_training.json` guide (chained-dialog reference): it walks App Settings first to enable the folder-browser picker (`#settingsBtn` awaitSwalOpen → `#swal-merge-picker` "tick this checkbox to show multiple files to merge" → `.swal2-confirm` Save), then `#merge-file-btn` (awaitSwalOpen) → **dialog 1** "Select Files" (`#merge-pick-accordion`, `#merge-pick-toggle-all`, `.swal2-confirm` **Next** flagged `chainsDialog`) → **dialog 2** "Merge CSV Files" (`.merge-file-row`, `#merge-add-btn`, `#swal-output`, `.swal2-confirm` Merge). The dialog-1 steps only appear when the picker is on — which the guide just enabled, so the happy path is consistent; if the user defies the instruction and leaves it off, those steps 3s-poll-then-skip (graceful degradation). **The richer dialog flows are full `guide_training.json` guides** (not slash-only) so free-text queries reach them, translated in 6 languages, with `/…` slash commands routing to them via `action: 'guide'`: `edit_file` (opener `#file-selection`, `awaitSwalOpen`, expands `file-sel-collapse`+`json-sel-collapse` → `#swal-input-filename` → `#toggle-mode` (`dialogStep`) → `.swal2-confirm`); `edit_calibration_curve` (opener `#cal-json-sel-section` → same dialog steps); **`app_settings`** — the gear opener (`awaitSwalOpen`) then **one dialog step per settings section** (`#swal-ui-language` General, `#swal-theme` Appearance, `#swal-mode` Measurement, `#swal-file-sort` File Selection, `#swal-log-timeout` Colorimeter Reading, `#swal-chart-height` Data Display, `#swal-ai-feedback-enabled` AI Assistant) → `.swal2-confirm` Save. Skip the frozen-build-only Data-folder field (`#swal-data-root-current`, guarded by `IS_FROZEN`) — targeting it would 3s-stall in dev. `#swal-*` field IDs are auto-detected as dialog steps by the `/swal2|#swal-/` heuristic (no `dialogStep` flag needed). **A dialog flow with more than one in-dialog step must introduce each key control / section**, not just the first — a single-element dialog step under-explains the dialog (the old one-step `app_settings` that only pointed at the gear was the anti-pattern). **`generate_report_dialog`** walks the **Report Details** dialog fired by Generate Report (`#generate-report-btn`, `awaitSwalOpen`) → `#swal-input1` Title → `#swal-metrics` (Calibrate-Kinetics) → `#swal-timepoints` (Calibrate-Point) → `#swal-xlabel` (Calibrate axis labels) → `input[name="swal-fmt"]` Format → `.swal2-confirm` build. The three middle fields exist **only in Calibrate mode** (and metrics vs time-points depend on the cal sub-mode), so each is flagged **`optional: true`**. It carries `requires_data_loaded` + `requires_mode: [kinetics, point, calibrate]` so the launcher prepends file-select / switch-to-a-data-mode steps as needed. **It must be launched BEFORE the dialog opens** — the Swal is modal, so the chat widget is unreachable once it is up. Both report entry points route here: the **`/report`** slash command's **Quick** choice (`_runReportChoice` → `_runGuideById('generate_report_dialog')`) and the free-text report quick/full clarify's **quick** branch (`deterministic_events`). The old `report_quick`/`report_quick_from_report` guides (which stopped at the button) were removed. **Anti-pattern**: do not add a dialog step whose only purpose is "click Generate quick Report" and stop — continue into the dialog, since the user can't ask for more help once it is open.
  - **`optional: true` for mode-conditional dialog fields.** When a dialog step targets a field that only exists in some modes, flag it `optional`: `showStep`'s not-found branch shortens its poll to ~0.4s (`maxChecks = step.optional ? 4 : 30`) before advancing, instead of stranding the user on a 3-second "searching…" tooltip for a field that doesn't apply. Like `awaitSwalOpen`/`dialogStep`, `optional` must be carried through `startCustomSteps` (the field-whitelisting step rebuilder) and survives `_localizeSteps` via `{...s}`. Use it only for genuinely-conditional in-dialog fields — a plain missing target should still get the full 3s grace (it may be mid-mount).
  - **Anti-patterns**: do not attach the normal interaction handler to a dialog step (double-advance); do not elevate the guide overlay for a dialog step (it darkens the dialog); do not drive advancement off a click on a `.swal2-confirm`/input (the element is torn out on close — watch for close instead); do not gate `_isSwalStep` on the literal string `swal2` only (the app's `#swal-*` in-dialog IDs would be missed and buried under the modal). **To let the AI author dialog flows** from free text, the Swal selectors + examples must be added to `trigger_custom_steps` on both the desktop tool schema and the `online` proxy (not yet done — these are local slash commands).
- Conversation history is **client-side only** (stored in `ai-chat.js` `AI.messages` array) — the backend is stateless, consistent with the single-user no-session rule.
- **Edit-and-resend**: user messages that are LLM queries are rendered editable (`_addEditableUserMsg`, hover-pencil → inline textarea → Save & resend / Cancel). Saving truncates `AI.messages` at that message's index and re-sends the new text through `_sendToLLM`, so every reply after the edited turn is discarded — matching ChatGPT-style edits. The `msgIndex` stored on the bubble is the message's position in `AI.messages`; this stays valid because the history is only ever appended to or truncated from the end (never shifted from the front). Slash-command/guide echoes use the plain `_addMsg('user', …)` and are **not** editable. Editing is blocked while a reply is streaming (`AI.currentAbort`). The edit-UI strings live as per-language maps keyed by `AI.activeLang` (`_EDIT_HINT`/`_EDIT_SAVE`/`_EDIT_CANCEL`), like the rest of the chat widget — they are **not** `ui_translations` keys (chat language is independent of `ui_language`). **Anti-pattern**: do not make guide/slash echoes editable, and do not key the edit off a DOM position — use the stored `msgIndex` into `AI.messages`.
- **New conversation**: a header **+** button (`#okapi-ai-new-btn`) → `OkapiAI.newChat()` starts a fresh chat — clears `AI.messages`, resets `AI.lastAction`, wipes the on-screen messages, and re-shows the welcome. It confirms first via `Swal` when a visible conversation exists (translated `_NEW_CHAT_CONFIRM_*` maps; falls through to an immediate reset when `Swal` is absent or the chat is empty). This is the discoverable button form of the `/clear` slash command (which still only empties history).
- **Answer feedback + learned matcher weights** (`src/ai_feedback.py`, `/ai/feedback`): every assistant answer gets a 👍/👎 row (`_attachFeedback` in `ai-chat.js`); 👎 reveals an optional comment box (Send / Skip both record the down-vote). All ratings are appended to `ai_feedback.jsonl`. When the rated answer was a **locally matched guide** (`source == "guide"` with a `guide_id` from `/ai/match`), the rating also tunes a per-guide coefficient in `ai_guide_weights.json` (`{guide_id: {weight, terms}}`): a 👍 raises `weight` (+`_UP_STEP`) and appends the query's content words to `terms`; a 👎 lowers it (−`_DOWN_STEP`), clamped to `[_MIN_WEIGHT, _MAX_WEIGHT]`. `_match_guide_example` adds `learned_terms` as extra keywords **before** the 0.1 baseline gate and `learned_bonus` to the score **after** it — so a 👍 makes similar queries match more confidently and ~5 👎 push even a strong, mode-boosted match below the launch threshold, while a positive weight can **never** make a zero-keyword (unrelated) guide fire. **LLM answers are logged only** — Groq is a third-party model that can't be retrained here, so they carry no `guide_id` and move no weight. Feedback on slash-command/button-launched guides is intentionally **not** offered (those are deterministic, not matched — reinforcing them would pollute the signal). Both files live in `state.script_dir` (alongside `ai_settings.json`), are gitignored, and are in `update_service._PRESERVE`. The feedback-UI strings are per-`AI.activeLang` maps (`_FB_*`), not `ui_translations`. **Anti-patterns**: do not apply `learned_bonus` before the baseline keyword gate (a 👍 would let a guide hijack unrelated queries); do not attempt to "improve" the LLM from feedback (Groq can't be retrained); do not log feedback to a path outside `state.script_dir`.
- **Feedback management + opt-out**: App Settings → **AI Assistant** exposes an `ai_feedback_enabled` user setting (default on), an **Export feedback** button (`GET /ai/feedback/export` → zip of both files) and **Reset learning** (`POST /ai/feedback/reset` → deletes both files); `GET /ai/feedback/stats` feeds the summary line. When the toggle is **off**, `_attachFeedback` hides the 👍/👎 row, `POST /ai/feedback` no-ops (`{recorded:false}`), and `_match_guide_example` ignores all learned weights — gated by `ai_feedback.is_enabled()`, read **once per match** (never in the per-guide loop). The two files are **already preserved/archived** outside this feature — in-app updates keep them via `_PRESERVE`, and the Windows uninstaller's data-folder backup ZIP includes them — so do **not** add a separate uninstall/update hook for them. **Anti-pattern**: do not call `is_enabled()` inside the per-guide scoring loop (one `user_settings.load()` per example per query).
- **Anti-pattern**: Do not add Ollama, local model pulls, or `pull_model`/`pull_status` routes — the app no longer uses a local model server.

### 2.15 Auto-Update — In-Place Code Update

- Auto-update is handled by `src/update_service.py` and `src/routes/update_routes.py` (`update_bp`, mounted at `/update/*`).
- **Version check**: `GET /update/check` calls `GET <AI_SERVICE_URL>/api/version` (unauthenticated or with Bearer token) and returns `{current, latest, update_available, release_notes}`.
- **Apply update**: `POST /update/apply` streams SSE events `{pct, label}` while downloading the zip via `GET <AI_SERVICE_URL>/api/download` (requires `Authorization: Bearer <license_token>` plus an `X-Machine-Id` header — the server hardware-checks the token, see §2.17), extracts it in-place over `state.script_dir`, then restarts the process.
- **Preserved paths**: `data/`, `report/`, `json/`, `log/`, `activation.json`, `ai_settings.json`, `user_settings.json`, `.env` are **never overwritten** by an update zip — they contain user data and credentials.
- **Zip convention**: The update zip may have a single top-level directory prefix (GitHub archive convention). `update_service._shared_prefix()` detects and strips it automatically.
- **Updates install dependencies**: `download_and_apply()` only overwrites source files — it does **not** rebuild the venv. So after `_apply_tarball()` it runs `_install_requirements()` (`pip install -r requirements.txt` via `sys.executable`, idempotent) so an update that adds a new package doesn't relaunch into an `ImportError`. A pip failure raises, so the caller reports the update as failed instead of relaunching a broken app. The in-app update is otherwise **not** responsible for venv corruption — it never touches `venv/` (gitignored, absent from the tarball) and never deletes files; a broken venv comes from the *installer* rebuild racing a locked, still-running instance (see the venv-health rules below).
- **Process restart**: `restart_after_delay()` uses `os.execv` on Mac/Linux (atomic in-place image replacement). On Windows it spawns a **detached PowerShell relauncher** (`_restart_windows()` / `_build_windows_relaunch_script()`) that waits for the dev-server port to be released, starts a fresh hidden instance, and shows a dialog if the app never comes back up — and only then frees the port via `os._exit(0)`.
- **Windows restart anti-pattern**: Do **not** revert to spawning the new instance *before* `os._exit(0)` on Windows. The old code raced the dying process for port `5099`, failed to bind (`app.run` → `sys.exit(1)`), and — being launched `-WindowStyle Hidden` — died with no visible window, bricking the app until the stray process was killed. The relaunch must happen only after the old process has freed the port.
- **Windows relaunch argument quoting**: The app installs to `C:\Program Files\EasyOKAPI` (path contains a space). `Start-Process -ArgumentList` joins its elements with spaces and does **not** quote elements that contain spaces, so each child argument must be embedded in double quotes (`_ps_arg()` produces a PowerShell literal like `'"C:\Program Files\...\main.py"'`). Passing a bare path makes Python receive a split argv (`C:\Program`), fail to find the script, and — being hidden — die silently so the app never comes back. `-FilePath` and `-WorkingDirectory` are single-value params and use plain single-quoting (`_ps_quote()`); only `-ArgumentList` needs `_ps_arg()`. This mirrors `launcher.ps1` (`-ArgumentList "`"$app`""`).
- **Windows relaunch port probe**: `_build_windows_relaunch_script()` probes the port with a .NET `TcpClient` connect to `127.0.0.1:<port>` (`Test-Listening`), **not** `Get-NetTCPConnection`. That cmdlet lives in the NetTCPIP module which is absent on some Windows builds; the old code's fallback there (`Start-Sleep -Seconds 3`) re-introduced the port race. Do **not** probe with "can I bind a `TcpListener`?" — `SO_REUSEADDR` lets a bind succeed while the dying process still holds the port, so only "can I connect?" reliably means "still listening".
- **Hidden-launch crash logging**: `launcher.ps1` starts Python `-WindowStyle Hidden -RedirectStandardError "$ScriptDir\code\log\launch_stderr.txt"`. Without the redirect, a startup traceback (broken venv, missing wheel, AV quarantine, elevation issue) is lost and the app silently "never starts" with no clue. The launcher creates the `log/` dir before launch because `state.py` only makes it *after* Python has imported far enough to run. Keep the redirect on any change to the launch `Start-Process`.
- **Stop the running app before touching its venv**: A live EasyOKAPI instance keeps its venv `python.exe`/DLLs open, so an in-place reinstall can only *partially* delete the venv (`pyvenv.cfg` vanishes, `python.exe` is stuck) and `pip install` into it fails with `[WinError 5] Access is denied` — the install then ships broken. `startwindow-4-venv.bat` therefore stops any `python.exe`/`pythonw.exe` whose `ExecutablePath` starts with the install root (`%~dp0`) and sleeps ~2s before rebuilding. The same requirements install succeeds into a writable, *unlocked* path (e.g. TEMP), which is the tell that a lock — not a bad package — is the cause. **Anti-pattern**: do not `rmdir` or `pip install` over a venv that a running instance may still hold open.
- **Venv health is verified, not assumed**: A venv `python.exe` aborts immediately with `No pyvenv.cfg file` if `pyvenv.cfg` is missing, so the app's hidden process dies before `main.py` runs. Two guards exist and must stay: (1) `launcher.ps1` preflight (at `p -eq 61`) refuses to launch unless `code\venv\pyvenv.cfg`, the venv `python.exe`, **and** `code\venv\Lib\site-packages\flask` all exist — otherwise it shows "Python environment is incomplete or corrupted. Please reinstall." (2) `startwindow-4-venv.bat` rebuilds the venv when `pyvenv.cfg` is absent (not just when `python.exe` is — a half-built venv used to survive reinstall), checks the exit code of **every** `ensurepip`/`pip install` step (`if errorlevel 1 → exit /b 1`), and ends with `python -c "import flask, pandas, requests, scipy, groq"` so a partial install aborts the installer instead of shipping a broken app. **Anti-pattern**: do not gate venv rebuild on `python.exe` existence alone, and never run a `pip install` without checking `errorlevel`.
- **Port cleanup is OS-aware**: `browser_mgt.close_port()` dispatches to `lsof`+`kill` on Unix and `netstat -ano`+`taskkill` on Windows. Do not assume `lsof`/`kill` exist on Windows (they don't — the old single-path version silently no-op'd there).
- **UI**: A version badge (`#app-version-badge`) in the top-left header gets an amber pulsing dot when an update is found. Clicking it opens a SweetAlert2 modal with release notes and an "Update Now" button. A progress bar modal shows SSE download/apply progress.
- **Anti-pattern**: Do not call `restart_after_delay()` from any code path other than the update apply route — it hard-exits the server process.

### 2.16 Data-Archive Layout (Uninstall / Reinstall)

- The **installers** (`installer-win/setup.nsi`, `installer-mac/setup.sh` + `uninstall.command`, `installer-linux/install.sh` + `uninstall.sh`) preserve `data/`, `json/`, `report/` across an uninstall/update by copying them to a persistent backup (`EasyOKAPI_data` in Documents/home) and restoring on the next install. The in-app auto-update (`update_service.py`) does **not** archive — it preserves data in place — so this layout logic lives **only** in the installers, not in `update_service.py`.
- **`data/` is normalized to a purely subfolder-based tree in the archive.** On backup, loose files sitting directly in the data root are moved into a `data/root/` staging folder ("normalize"); on restore, `data/root/`'s contents are moved back up to the data root and the folder is removed ("restore"/dissolve). This keeps the archived `data/` tree uniform so it round-trips cleanly. `json/` and `report/` are **not** normalized (they are already subfolder-organized).
- The staging folder name (`root`) is the reserved folder name from §2.6 — the app forbids creating a real `data/root/` so the staging folder never collides with user data.
- **Implementation is inline in each installer (no shared Python helper)** — at Windows restore time no Python interpreter exists yet (the venv is built in a later step), so the logic must be installer-native. Windows uses a small PowerShell script written to `$PLUGINSDIR\archive.ps1` (the `WriteArchiveHelper` / `RunArchive` NSIS macros, mirroring the `stop-easyokapi.ps1` file-not-inline pattern); Mac/Linux use shell `_archive_stash_root` / `_archive_unstash_root` functions (`find -maxdepth 1 -type f`).
- **Anti-pattern**: Do not normalize the *live* install's `data/` directory — only the backup copy (on archive) and the restored copy (on restore), so a failed install never mutates the user's working data. Do not add normalization to `json/` or `report/`.

### 2.17 Hardware-Locked Activation

- A **permanent activation token is bound to one machine**, so copying `activation.json` (or the whole install folder) to another computer must not unlock the app. Three layers enforce this; do not weaken any in isolation:
  1. **Fingerprint** — `src/hwid.py` `get_hwid()` returns `SHA-256("easyokapi-hwid-v1|<os>|<raw-id>")` where `<raw-id>` is the Windows `MachineGuid` / macOS `IOPlatformUUID` / Linux `/etc/machine-id`. **The Windows installer's PowerShell (`installer-win/setup-frozen.nsi`) reproduces this recipe byte-for-byte** — if you change the salt (`_HWID_VERSION`), the `win` branch, or the canonical string, update that PowerShell or first-launch verification breaks. Read `MachineGuid` from the **64-bit** registry view on both sides.
  2. **Asymmetric signing** — permanent tokens are **RS256**. The server signs with `ACTIVATION_PRIVATE_KEY` (env, never committed); the client embeds only the public half (`src/activation_pubkey.py`). `activation.verify_token()` verifies the signature offline **and** checks the `hwid` claim equals `get_hwid()`. The client must never hold a secret that can mint tokens — keep the private key off the client.
  3. **Server enforcement** — `license_machines` (`(user_id, hwid)`, seat cap `MAX_MACHINES_PER_LICENSE`, default 1). `/api/activate` binds; `/api/download`, `/ai/proxy/chat`, `/api/version` re-check the presented `X-Machine-Id` / `hwid` against the token and seat. Transfer is `POST /api/account/machines/deactivate` (needs a web session).
- **Uninstalling must free the seat.** A seat is held until it is explicitly released, so a deleted install would otherwise hold the cap forever and refuse the user's next machine. Every uninstaller calls **`POST /api/license/release`** *before* removing anything (`installer-win/setup-frozen.nsi` `Section "Uninstall"` → `release-seat.ps1`; `installer-mac/uninstall.command` and `installer-linux/uninstall.sh` → `_release_license_seat`). `activation.release_machine()` is the same call in Python, for in-app/source use.
  - Auth is the machine's **own permanent token**, not a session — there is none at uninstall time. The token's `hwid` claim **names the only seat it may free**, so a machine can only release itself. Never fall back to a body-supplied `hwid` to pick the seat: that would let any token free any machine's seat.
  - Because the claim names the seat, the uninstallers need **no hwid recipe** — only `setup-frozen.nsi`'s *install-time* activation mirrors `src/hwid.py` (see above). Do not add a second PowerShell/shell copy of the fingerprint recipe here.
  - The uninstall shells find `activation.json` via the **`.easyokapi_dataroot` pointer** (default root otherwise) — the same resolution `src/state.py` uses — then the install dir for source installs.
  - **Best-effort, never blocking**: no token, no network, or a refusal must not stop an uninstall. When the server is unreachable the user is told to deactivate from their account, since the seat stays taken.
- **Anti-pattern — deleting a revoked seat**: neither `/api/license/release` nor `/api/account/machines/deactivate` may free a seat with `revoked=True`, or belonging to a `banned` user. Deleting the row lets the same machine re-activate into a fresh, unrevoked seat and walk straight out of the admin kill-switch (§2.17 revocation). Both routes refuse with 403.
- **Known gap**: the macOS **frozen** build (`/Applications/EasyOKAPI.app`) is removed by dragging it to the Trash, which runs no script, so its seat is not released. Those users must deactivate from their account page.
- **Backward compatibility**: legacy HS256 tokens (no `hwid`) are grandfathered by `verify_token()` while `_ALLOW_LEGACY_HS256` is `True`. An HS256 token that *claims* an `hwid` is treated as tampering and rejected. Flip the flag to `False` once every install has re-activated.
- **Dependencies**: offline verification needs `PyJWT[crypto]` + `cryptography` (in `requirements.txt`, bundled via `easyokapi.spec` hidden imports). Dev/source builds are never gated (`needs_activation()` is False unless `sys.frozen`), and `verify_token()` falls back to claim-only checks when the libs are absent so developers are never blocked.
- **Anti-pattern**: do not check the `hwid` claim without also verifying the RS256 signature (a hand-written token could then fake any `hwid`); do not embed the private key in the client; do not let the two hwid recipes (Python vs PowerShell) drift.

### 2.18 Windows Elevation & Running-Instance Guard (Frozen Build)

- **`EasyOKAPI.exe` must NOT force elevation.** Do **not** set `uac_admin=True` in `easyokapi.spec`. An unsigned PyInstaller EXE that embeds a `requireAdministrator` manifest matches Windows Defender's ML heuristic for droppers and gets flagged as **`Trojan.Win32C!ml`** (a false positive that blocks the install). The app runs at the user's normal (medium) integrity. The §1 "no admin" rule stands for the frozen build too. *(If per-machine elevation is ever truly needed, it has to come together with Authenticode code-signing — see below — not a bare manifest on an unsigned binary.)*
- **Installer/uninstaller still elevate** via NSIS `RequestExecutionLevel admin` (they need to write the hosts file, Program Files, etc.). That is unrelated to the app's own integrity level.
- **Code-signing / AV note**: the EXE and NSIS installer are currently **unsigned**, so `!ml` false positives can recur intermittently regardless of the manifest. The durable fix is Authenticode signing (an EV cert gives near-instant Defender/SmartScreen reputation) plus a false-positive submission to Microsoft. Until then, avoid changes that raise the heuristic score (no `requireAdministrator` manifest, no UPX — `upx=False` already, keep onedir).
- **In-app update swap elevates on-demand, NOT via a manifest.** The frozen install lives under `%PROGRAMFILES%` (admin-only) but the app runs non-elevated, so the binary-swap updater (`update_service._spawn_windows_swapper`) cannot replace the install dir itself. It writes two scripts and spawns a **non-elevated coordinator** (`_build_windows_coordinator_script`) that: waits for the app's port to free → launches an **elevated helper** (`_build_windows_swap_script`, run via `Start-Process -Verb RunAs` = one UAC prompt) that does ONLY the `Move-Item` swap + `icacls /reset` and writes an `OK`/`FAIL:` result file → then, back in the non-elevated coordinator, relaunches the app and clears the pending-swap marker. All steps log to `<script_dir>\log\update_swap.txt`.
  - **Anti-pattern — relaunching from the elevated context**: the app must be relaunched by the **non-elevated** coordinator, never by the elevated helper. A child of the elevated process inherits admin integrity, so it would write the user data dir (`Documents\EasyOKAPI`) as admin and break later non-elevated writes.
  - **Anti-pattern — clearing the pending marker before the swap is confirmed**: `apply_pending_swap_and_exit()` must NOT clear `_pending_update.txt` on Windows; only the coordinator clears it *after* the elevated helper reports `OK`. Clearing it unconditionally orphans the staged bundle when the swap fails / UAC is declined — the silent "update runs to 100% but reopens on the old version" bug.
  - **Anti-pattern — spawning the coordinator via bare `'powershell'`**: a frozen PyInstaller process can run with a **stripped/sanitised `PATH`** that omits System32, so `subprocess.Popen(['powershell', ...])` raises `FileNotFoundError` and the swap coordinator never launches (the scripts get written, but no swap and no `update_swap.txt`). Always resolve the absolute interpreter via `update_service._powershell_exe()` (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, falling back to bare `powershell` only if absent) for every Python-side `Popen` of PowerShell — both `_spawn_windows_swapper` and `_restart_windows`. (Inside an already-running PS script, bare `powershell` is fine.)
  - **Anti-pattern — swallowing the swap-handoff exception**: `update_routes._delayed_shutdown()` must NOT discard a failure from `apply_pending_swap_and_exit()` with a bare `except: pass`. A spawn/handoff failure used to vanish (app fell through to a normal shutdown, reopened on the old version, no trace). Record it via `_log_swap_failure()` to `update_swap.txt` before falling through to the SIGTERM shutdown.
  - **Anti-pattern — `DETACHED_PROCESS` when spawning the coordinator/relauncher** (the real root cause of the "update never applies" bug): `powershell.exe` is a console application. `CreateProcess` with `DETACHED_PROCESS` (`0x8`) gives the child **no console**, so the PowerShell host fails to initialise and the process **exits before running a single line** — `Popen` still returns a valid PID, so nothing raises and nothing logs; the scripts are written but no swap and no `update_swap.txt` ever appear. Spawn the detached coordinator with **`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`** only (NO `DETACHED_PROCESS`). `CREATE_NO_WINDOW` runs it hidden *with* a console, and the child still outlives the exiting app. Same rule for `_restart_windows`. Empirically: any flag set containing `DETACHED_PROCESS` → child never runs; `CREATE_NO_WINDOW` / `CREATE_NEW_CONSOLE` / no-flags → child runs. (Unix uses `start_new_session=True`, which has no console concept and is fine.)
  - **Anti-pattern — running the coordinator with the install dir as its cwd**: the `Popen` in `_spawn_windows_swapper` MUST pass `cwd=state.script_dir` (the data dir). The coordinator inherits the app's cwd — the install dir (`$live`, set by the launcher's `-WorkingDirectory`) — and stays alive (waiting on the elevated swap) during the move. Windows cannot rename a directory that is a running process's current directory, so the elevated `Move-Item $live $old` fails and the new build ends up **nested inside the old install** (`EasyOKAPI\EasyOKAPI`). Never let any still-running helper hold `$live` as its cwd.
  - **Anti-pattern — the elevated swap script without `$ErrorActionPreference = 'Stop'`**: PowerShell cmdlet errors (`Move-Item`, `Remove-Item`, …) are **non-terminating** by default, so a `try/catch` does NOT catch them. Without `Stop`, a failed "move `$live` aside" falls straight through to "move `$new` in" — and since `$live` still exists, `Move-Item` **nests** the new build inside it and the script still writes `OK` (a false success that also clears the marker). The swap helper must set `$ErrorActionPreference = 'Stop'` so a failed move is terminating → caught → rolled back → reported `FAIL` → marker kept for retry. Keep only the two directory moves fatal; wrap the Uninstall-copy / `.old` cleanup / `icacls` as best-effort so they can't turn an applied swap into a false failure (or trigger a rollback over the new install). Guard with `if (Test-Path $live) { throw }` before the second move so nesting can never happen.
  - This transient `RunAs` is allowed; it does **not** violate the "no `requireAdministrator` on `EasyOKAPI.exe`" rule above — the EXE itself still ships with no elevation manifest.
- **The installer and uninstaller refuse to touch a running instance.** Both the install-side overwrite guard and the `Section "Uninstall"` in `setup-frozen.nsi` write a `detect-easyokapi.ps1` (exit 1 = running, 0 = clear) with **two independent fail-safe signals**: (1) any `EasyOKAPI.exe` from `Get-CimInstance Win32_Process` whose `ExecutablePath` starts with the install dir — or whose path is unreadable — counts as running; (2) a **file-lock test** (`[System.IO.File]::Open($exe,'Open','ReadWrite','None')` throws ⇒ exe is in use). The lock test is the definitive, integrity-independent "can I delete these files" check. Keep both detectors identical.
  - **Anti-pattern — trailing backslash in the passed path**: do **not** pass the install dir as a quoted argument ending in a backslash (`... detect-easyokapi.ps1" "$INSTDIR\"`). On the Windows command line `\"` is an escaped quote, so `"C:\…\EasyOKAPI\"` is mangled, `$args[0]` no longer matches `ExecutablePath`, the `StartsWith` fails, and the check silently reports "not running" → destructive `RMDir` against a locked folder. **Bake `$INSTDIR` into the script** via `FileWrite $9 "$$r = '$INSTDIR'$\r$\n"` (single-quoted; backslashes/spaces are literal in a PS single-quoted string) and invoke the script with **no path argument**.
  - **Anti-pattern**: do not gate the process match on `-and $_.ExecutablePath` (drops processes whose path is unreadable → false "not running").
- **The uninstall is cancellable.** `Section "Uninstall"` opens with a `MB_YESNO` confirmation (No → `Quit`, nothing removed), and the running-instance prompt's Cancel also `Quit`s. Keep an explicit, non-destructive bail-out path before any deletion.

### 2.19 User-Selectable Data Root

- The writable data root (`state.script_dir`) holds every user artifact (`data/`, `json/`,
  `report/`, `log/`, plus `user_settings.json`, `activation.json`, `ai_settings.json`, `.env`,
  markers). In a **frozen build** the user may relocate it from **App Settings** onto another drive
  or a shared folder. The default stays `<Documents>/EasyOKAPI` (win/mac) / `~/EasyOKAPI` (linux).
  **Source/dev runs always use the project root and ignore all of this.**
- **The Windows installer lets the user choose the data location.** `setup-frozen.nsi` adds a custom
  themed **Data Folder** page (`DataFolderPage`/`DataFolderPageLeave`) after the Directory page, so
  `$INSTDIR` is known for validation. The user picks a *parent* folder (`$DataParent`, default
  `$DOCUMENTS`); the data root is `$DataParent\EasyOKAPI`. When the choice is non-default the Install
  section writes the `$DOCUMENTS\.easyokapi_dataroot` pointer the app reads on launch; when it's the
  default it deletes any stale pointer. The page **rejects** `$INSTDIR` / anything under Program Files
  (mirrors the in-app safeguard). Relocation afterwards is an in-app action.
- **The Windows uninstaller is pointer-aware.** `setup-frozen.nsi`'s `Section "Uninstall"` reads
  `$DOCUMENTS\.easyokapi_dataroot` and acts on the **relocated** folder when it exists (prompt, backup
  ZIP, removal); on removal it also wipes the default folder + both `_data` siblings + the pointer
  file, so a leftover copy from an in-app relocation never lingers. Because the pointer is a sibling
  it still works when the default folder is gone. (The mac/linux uninstall scripts are source-build
  only and do not touch the frozen data folder.)
- **Relocation MOVES, except away from the default (which copies).** `data_root.set_data_root(parent_dir)`
  copies the *whole* current root into an **`EasyOKAPI` subfolder of the chosen folder**
  (`<parent>/EasyOKAPI`) and points the app there. The copy skips the `.dataroot` pointer and transient
  `_update*` artifacts (`_copy_ignore`). After the copy + pointer write, the **original is deleted (a
  move)** — *unless* it is `state.default_data_root`, which is kept as a fallback (a "copy"). So
  relocating an already-relocated folder, or `reset_to_default()` (custom → default), removes the old
  custom folder; relocating away from the default keeps it. `_relocate(target)` returns
  `(path, moved)`; `POST /data_root` surfaces `moved` so the UI says "moved" vs "copied". Both callers
  go through `_relocate` → `_validate_target` (absolute; not a file; not inside `bundle_dir` — i.e. the
  EasyOKAPI program folder; not equal to / inside the current root; parent writable). The pointer is
  written **before** the source is removed, so an interrupted move never aims the pointer at a deleted
  folder.
- **The location lives in a `.easyokapi_dataroot` pointer file, NOT in `user_settings.json`.**
  `user_settings.json` lives *inside* the data root, so it cannot record where the data root is
  (chicken-and-egg). The pointer is a one-line file holding the absolute path, kept **beside** the
  default folder — i.e. in its parent (`<Documents>`/`<home>`, deterministic per OS), **not inside
  it**. Keeping it outside means the pointer (and the link to the relocated data) **survives the user
  deleting the now-empty default folder**, so both the app and the uninstaller can still find the real
  data. On Windows the parent is exactly NSIS's `$DOCUMENTS`, so the uninstaller reads the same file.
  `state._read_dataroot_override()` reads it at import; `data_root._write_pointer()` writes/clears it;
  `state._dataroot_pointer_path()` is the single source of truth for its location.
- **The move is deferred-commit, in two steps.** Resolution is import-time, so changing the root
  **requires an app restart** — and nothing is moved until the user accepts that restart. **Step 1**
  `POST /data_root` is a **dry run**: `data_root.preview_data_root(parent)` / `preview_reset()` validate
  the choice and return `{path, moved, restart_required: true}` **without touching the filesystem**. The
  UI confirms, offering **Restart now** / **Cancel**. **Step 2 — Restart now** re-sends the same body to
  `POST /data_root/restart`, which is where the copy/move actually happens (`set_data_root` /
  `reset_to_default`), then relaunches the app in place via `update_service.restart_after_delay()`
  (mac/linux `os.execv`; Windows detached relauncher) and serves `restarting.html` — a page that polls
  `/ping` and reloads the tab once the fresh instance rebinds the same port, so the new data location
  takes effect with no manual relaunch. **Cancel** is a true no-op: since nothing was committed, the
  data stays exactly where it was (no revert needed).
- **The folder is picked with an in-app browser, not a typed path.** `GET /browse_dirs?path=` lists a
  directory's non-hidden subfolders (and Windows drives via `?path=::drives`) for the SweetAlert
  navigator (`pickDataRootFolder` in `init.js`); the server then appends `EasyOKAPI`.
- `GET /data_root` returns `{current, default, is_custom}`, injected into `index.html` as
  `DATA_ROOT_INFO` (with `IS_FROZEN`); the settings modal hides the section for source builds.
  `POST /data_root` (`{path}` to relocate, or `{reset:true}`) is frozen-only, `@423 LOCKED` while the
  data-collection process runs; it **previews only** and returns `{path, moved, restart_required}`.
  `POST /data_root/restart` (same `{path}`/`{reset:true}` body + `mode`) commits the move and relaunches,
  serving `restarting.html` on success (or a JSON error on a commit failure); it carries the same
  frozen + `@423 LOCKED` guards.
- **Anti-patterns**: do **not** store the data-root path in `user_settings.json`; do **not** point
  the data root inside `bundle_dir` / the EasyOKAPI program folder (read-only, elevated — rejected
  both in `_validate_target` and on the installer's Data Folder page); do **not** delete the **default**
  folder on relocation (only a *non-default* source is removed — the default is the fallback); do
  **not** write the pointer *after* removing the source (write it first); do **not** move data in
  `POST /data_root` — it is a **dry run** (preview only) so a cancel needs no revert; the actual move
  and the relaunch are confined to `POST /data_root/restart`.

### 2.20 Default Display on Restart

- A **restart** (`POST /data_root/restart` relocation, or `POST /update/finalize` after an applied
  update) must bring the app back up in the **default display** — kinetics mode with fresh per-view UI
  state — not the previous tab's saved `localStorage` layout. The restart reloads the same browser
  origin (same tab for the data-root in-place relaunch, a new tab for the manual post-update relaunch),
  so client-only `localStorage` survives the process restart by itself; resetting requires a signal that
  also survives it.
- **Mechanism**: the restart routes call `state.mark_reset_display_pending()` *before* triggering the
  relaunch. This writes a one-shot sentinel (`state._RESET_DISPLAY_MARKER`) in **`default_data_root`** —
  the stable folder where the `.dataroot` pointer lives, **not** `script_dir` — because a relocation
  restart changes `script_dir`, and the new process must still find the flag. The next `index` render
  calls `state.consume_reset_display_pending()` (reads **and deletes** the sentinel) and passes
  `reset_display` to the template. `index.html` exposes it as `const RESET_DISPLAY`; when true it drops
  per-view `localStorage` keys (keeping genuine cross-session prefs: `theme`, `okapi_ai_lang`,
  `okapi_ai_first_run`) **before** `init.js` runs, and `init.js` forces the kinetics mode button
  regardless of `USER_SETTINGS.default_mode`.
- **One-shot vs. the auto-opened tab (race)**: because the sentinel is consumed on the **first** index
  render, only **one** tab may load `/` during a restart. The in-place relaunch (`update_service.restart_after_delay`
  → `os.execv` / `_restart_windows`) re-runs `main.py`, which would normally auto-open a **second**
  browser tab. That tab would race the user's existing tab (reloading itself from `restarting.html`) for
  the marker; whichever lost would come up with `reset_display=false` — leaving the `#measurement-mode`
  button on the saved `default_mode` instead of kinetics. The relaunch therefore passes `--no-browser`
  (`update_service._relaunch_argv()`) so the fresh instance does **not** open a tab — the user's reloading
  tab is the sole marker consumer.
- **`AppState.reset()` mirrors the button**: `AppState.reset()` in `index.js` sets `currentMeasurementMode`
  from the selected `#measurement-mode` button's `data-value` (fallback `"kinetics"`), **not** a hard-coded
  `"kinetics"`. init.js sets that button before `reset()` runs (on `$(document).ready` and on server-down
  recovery), so the internal mode and the button highlight can never desync. Do **not** reintroduce a
  hard-coded mode in `reset()` — it silently diverges from the button whenever `default_mode` ≠ kinetics.
- **`switchingModes` runs on load**: `$(document).ready` calls `switchingModes(_initialMode, { silent: true })`
  **after** `initDefaultState()` so the selected mode's **section layout** (and, for report mode, the report
  directory) is realized on load — previously that ran only on a button click, so a non-kinetics `default_mode`
  came up with the kinetics layout. It must run after `initDefaultState()` (which hides sections point/calibrate
  need shown), and the `default_subfolder` auto-select is skipped in report mode (it would override the report
  directory). The `{ silent: true }` flag suppresses the `mode/switch` analytics event — this is the default
  layout, not a user-initiated switch; pass it for any non-interactive `switchingModes` call.
- **Anti-patterns**: do **not** put the sentinel in `script_dir` (lost across a relocation restart); do
  **not** make the reset a client-only flag (`sessionStorage`/query param) — it will not survive the
  manual post-update relaunch into a fresh tab; the flag is **one-shot** (consumed on first render) so a
  plain refresh keeps the user's layout — do not leave it set; do **not** clear `theme` (it would lose
  the user's chosen mode on every restart — it is preserved and re-derived from `USER_SETTINGS.theme`); do
  **not** let an in-place relaunch auto-open a browser tab (it races the user's tab for the one-shot
  marker — pass `--no-browser`).

### 2.21 Folder/file tables: Modified Date + Sortable Columns

- **All three folder/file tables** show a **Modified** column (last-modified date) and support
  click-to-sort on the **name** and **Modified** column headers: the CSV **File Selection** table
  (`#file-table`), the **calibration-JSON** table (`#json-table`), and the **report-subject folder**
  table (`#file-table` in report mode). Sort order is one of `name_asc` / `name_desc` / `date_asc` /
  `date_desc`; the **single shared** default is the `file_sort_order` user setting (default
  `date_desc`), persisted via `POST /settings` (helper `_applySortOrder()` in `navigation.js`) and
  re-applied on load. Sorting one table changes the shared order for all of them.
- **Date metadata is server-supplied.** `src/file.py` exposes `build_meta(directory, names, …)`
  (stats arbitrary names — used for report subject **directories**) and `get_file_meta(directory,
  fileType, …)` (globs files, delegates to `build_meta`). Each returns a `{name: {mtime, display}}`
  map. Routes that feed a table must also return its meta: index → `file_meta` + `cal_json_meta`
  (embedded as `FILE_META` / `CAL_JSON_META` consts); `/browse` → `files_meta`; `/get_json_cal` →
  `files_meta`; `/get_report_subjects` → `subjects_meta`. `mtime` (epoch) drives client-side date
  sorting; `display` is the cell text. JS keeps per-table maps on `AppState`
  (`fileMeta`/`jsonMeta`/`reportMeta`) refreshed from those responses.
- **The `display` time tag is formatted server-side** from the `time_tag_format` user setting
  (App Settings → General; `iso`/`iso_sec`/`us`/`eu`/`date_only`, default `iso`) via
  `TIME_TAG_FORMATS` in `file.py`. **Every** route that builds meta must pass the setting
  (`time_format=…`) so a format change re-renders live. Do not format the tag client-side — it would
  diverge from the first server paint, and `mtime` (not `display`) remains the sort key so changing
  the format never reorders rows.
- **Dual render — keep them in lockstep.** Each table is rendered **twice**: server-side Jinja in
  `index.html` (first paint, File Selection + calibration-JSON) and client-side render helpers in
  `navigation.js` (`renderFileRows` / `renderJsonRows` / `renderReportRows`, every refresh / re-sort).
  Both must produce the **same** column layout (name, Modified, then 3 action columns → empty/`+more`
  rows use `colspan="5"`) and the same clickable header markup (`sort{File,Json,Report}Table('name'|'date')`
  with the `.sort-arrow` indicator). The report-subject table is JS-only (report mode can never be the
  initial server render) so it has no Jinja half.
- **`filterFiles` still operates on plain name strings** — do not change `files`/`response.files` to
  carry dicts (it also feeds `deleteDataFolder`'s confirmation list). Sorting reads dates from the
  per-table `AppState.*Meta` maps, keyed by name, instead.
- **`updateJSONTable(undefined)` self-refetches.** Called with no argument (post-copy/edit refreshes)
  it re-fetches `/get_json_cal` for the current mode to get fresh files **and** meta; called with a
  list it renders directly. Do not pass a bare list expecting it to also refresh dates.
- **Anti-pattern**: do not sort or compute dates only on the client from `localStorage`/guesswork;
  do not give each table its own sort setting (the preference is intentionally shared via
  `file_sort_order`).

### 2.22 UI Localization (i18n)

- The whole UI is translatable into the **same 6 languages as the AI chat** (`en`, `vi`,
  `zh`, `fr`, `ja`, `ru`). The active language is the **`ui_language`** user setting
  (App Settings → General; default `en`), independent of the AI chat's own language.
- **Catalogs**: flat **key → string** JSON files in `ui_translations/<lang>.json`, shipped
  beside the app and resolved from **`state.bundle_dir`** (the read-only program folder — **not**
  `state.script_dir`, the writable data root), mirroring `ai_assistant.py`'s
  `guide_translations/`. `en.json` is the **baseline source of truth**; a non-English file is
  overlaid onto English, so any **missing key falls back to English**. Loading is best-effort and
  cached (`src/i18n.py` `load_catalog(lang)` / `normalize_lang(lang)`); a missing/broken file never
  raises into a request.
- **Server injection**: `core_routes.index()` computes `ui_lang` + `ui_strings` from the setting and
  injects them into `index.html` as `const UI_LANG` / `const UI_STRINGS`. `<html lang="{{ ui_lang }}">`.
- **Client applier** (`static/script/i18n.js`, loaded right after `short-hands.js`, before all other
  app scripts): exposes `window.t(key, fallback)` for dynamic strings and `window.applyTranslations(root)`
  which translates tagged elements on `DOMContentLoaded`. Attribute contract on elements:
  `data-i18n` → `textContent`, `data-i18n-html` → `innerHTML`, `data-i18n-hint` → `data-hint`,
  `data-i18n-ph` → `placeholder`, `data-i18n-aria` → `aria-label`. **The English text stays in place
  in the HTML as the fallback** — a missing catalog or source build still reads correctly.
- **Dynamic strings** (`Swal.fire(...)`, JS-built tables) use `t('key', 'English literal')`. The
  literal is the fallback, so an un-migrated dialog keeps working in English; migrate incrementally.
  `navigation.js` table re-renders (`renderFileRows`/`renderJsonRows`/`renderReportRows` + the header
  builders) must use `t()` so the JS re-render and the Jinja first paint stay in lockstep (Rule §2.21);
  `t` is global and loaded before `navigation.js`.
- **Changing the language reloads the page** (`init.js` settings save): the server re-renders with the
  matching catalog, so every static label and dynamic dialog comes up consistently translated — there
  is never a half-translated state and no live two-language switching.
- **Keep technical terms in English** in every catalog: mode names (`kinetics`/`point`/`calibrate`/`report`),
  units (`seconds`/`minutes`/`nM`/`ng/µL`), `Absorbance`, `maxRate`, `rSquared`, `Slope`, `Sat`, `Blank`,
  `ConcenUnit`, `CSV`/`JSON`/`Excel`, and brand names (`Easy OKAPI`/`EasyOKAPI`/`CBBiotec`/`CBB`/`PyBadge`).
- **Escape translated text before inlining it into markup.** The English literals are all quote-free, so
  string-concatenating them into HTML happens to work; the catalogs are not. French and Russian carry
  apostrophes (`Voir l'analyse`), which silently break any **single-quoted JS string inside a
  double-quoted HTML attribute** — the inline `onclick` pattern used by `data-display.js`
  `createToggleButton()`. That file exports two escapers, and a `t()` result reaching either context must
  go through the matching one: **`escapeAttrText()`** for a plain attribute (`data-hint="..."`), and
  **`escapeInlineHandlerText()`** for text embedded in an inline handler's JS (it emits `\'` for the JS
  layer and `&quot;`/`&lt;`/`&amp;` for the HTML layer, which the parser unescapes before compiling the JS).
  Prefer `setAttribute`/`textContent` over string-built markup for new code, which sidesteps both layers.
- **Placeholders** in catalog strings use the `{n}` / `{m}` token convention, interpolated at the call site
  with `t('key', 'English {n}').replace('{n}', value)` — there is no interpolation inside `t()` itself. Every
  language's copy of a placeholder string must keep the token (a dropped `{n}` renders a sentence with a
  missing number, silently).
- **Anti-patterns**: do **not** resolve the catalog dir from `state.script_dir` (it's the writable data
  root, not where the shipped catalogs live — use `state.bundle_dir`); do **not** add a UI string without
  giving it a key in **`en.json` and all five** `vi/zh/fr/ja/ru` files (keep them in lockstep — covered by
  `tests/test_i18n.py`, which fails on key drift); do **not** strip the in-place English text when adding a
  `data-i18n*` attribute (it is the fallback); do **not** translate the technical terms above; do **not**
  translate **chart series labels** (`getLabel`, `getLabelsFromYColumn`, `determineMeasurementLabel` in
  `data-display.js`) — they are built from file metadata, flow into report/Excel exports, and are matched
  against verbatim (e.g. `labels.toLowerCase().includes("absorbance")` in `findYDimension`).

### 2.23 Excel Export — Native Calibration Charts

- **Calibration fit charts must export as native, editable Excel charts, not baked-in PNGs.** A PNG
  freezes the axis text into pixels, so the user can't rename axes when they edit the workbook. The
  `/export_report_excel` route (`file_routes.py`) renders calibration "standards points + fit curve"
  charts as openpyxl `ScatterChart`s (`_add_native_scatter_chart`): two series — standards as
  markers (`Marker` + `graphicalProperties.line.noFill`), fit as a smooth line (`smooth=True`,
  `Marker('none')`) — with `chart.title` / `x_axis.title` / `y_axis.title` as live Excel objects.
  **You must set `x_axis.delete = False` and `y_axis.delete = False`** or openpyxl hides the axis
  titles entirely.
- **Data contract**: the client (`report.js`) sends each calibration chart as a `chart_series` entry
  (`{ label, title, algo, xLabel, yLabel, points:[{x,y}], fit:[{x,y}] }`) built by
  `buildScatterSeries()`, not as a `chart_images` base64 PNG. The backend prefers `chart_series` and
  falls back to embedding `chart_images` only when `chart_series` is absent (back-compat + non-calibration
  time-series snapshots). Keep both client export paths in lockstep — the per-view `generateReportExcelFromCurrent`
  **and** the multi-file report-console `finalizeReportExcel`.
- **Axis-label boxes**: both export dialogs expose editable, auto-filled X/Y label boxes (the
  `generateReport` SweetAlert `#swal-xlabel`/`#swal-ylabel`, and the console `#console-xlabel`/`#console-ylabel`).
  **X defaults to the concentration-unit-aware `Concentration (<unit>)`** (`_concenAxisLabel()` →
  `getMetaConcenUnit()`, the post-§2.10 `# ConcenUnit` schema — ng/µL, nM, %), matching the live chart
  (`generate-chart.js`) and the report's derived-concentration lines. `_concenAxisLabel()` is the **single
  source** for every calibration chart's X-axis — the native Excel `chart_series`, the PDF/PNG path
  (`renderCalibrationChartImage` via its `xLabel` arg, and the inline kinetics-cal canvases) — so do not
  reintroduce a bare-`Concentration` axis in any of them. The single-file `generateReport`
  dialog **pre-fills** the exact unit from `AppState.metaData`; the multi-file console box is left **blank =
  "auto" per file** (each chart uses its own file's `config.metadata` unit), because different files in one
  report can carry different units. **Y left blank means "auto" — each chart uses its own metric/measurement
  label** (`niceMetric` / `measLabel`). A non-blank box overrides every chart in that export. **Anti-pattern**:
  do not hardcode the X label to bare `Concentration` (it drops the unit — the obsolete pre-ConcenUnit
  assumption); do not force a single file's unit onto the multi-file console export.
- **Helper columns must stay visible.** Each native chart's X/Y values are written to off-to-the-right
  columns (col AA onward via the per-sheet `_chart_helper_col` cursor). Do **not** hide these columns or
  move the data to a hidden sheet — Excel does not plot data in hidden cells, which would blank the chart.
- **It is a category-axis `LineChart`, both series markers-only, on the FULL merged grid.** The standards+fit rows
  are merged and **sorted** by concentration (~157 rows); helper cols `conc` (AA), `std_y` (AB), `fit_y` (AC). Both
  series are **markers only** (no lines). Why this shape: the 150 *uniform* fit rows fill the category axis so a
  standard's row index ≈ its value position (proportional-looking, like the old shared-X scatter), **and** the
  X-axis labels come from the `conc` column which we write **only on the standard rows** — so the axis shows the
  measured **concentration-table values** and never the fit's generated Xs. (A value-axis scatter cannot do this:
  Sheets either drops a series or auto-picks round ticks like 50/200 — not the table values.) **Anti-pattern**: do
  not label the fit rows in `conc`; do not put all 150 fit Xs on the axis. Covered by `tests/test_report_excel.py`.
- **Labels = the standard concentrations.** `conc` carries each standard's concentration on its own row, blank
  elsewhere; both series share it as the `cat` reference. (`_nice_axis_ticks` is retained as a utility but the axis
  is **not** clamped — the labels are the actual table values, not a nice-number series, and Sheets ignores
  `majorUnit`/`number_format=';;;'` on this chart anyway.) Google Sheets may still thin a dense set of labels, but
  they are always concentration-table values. **Anti-pattern**: do not blank the labels or relabel with round ticks.
- **Series carry explicit numeric caches.** Series are built from the raw `XYSeries` class with
  `val = NumDataSource(numRef=NumRef(f=…, numCache=NumData(...)))` and `cat = AxDataSource(numRef=NumRef(…))` —
  each reference embeds a `<numCache>` of its values. openpyxl's `Series` factory writes *bare* refs with no cache:
  Excel recomputes them on open, but **Google Sheets does not** — a cache-less ref is read as text/empty and the
  series is dropped. **Anti-pattern**: do not fall back to the `Series(values, …)` factory.
- **Fit resolution.** `buildCalibrationRegressionLine` (and the inline regline loops in `report.js`) sample the
  curve at **150 points** so it reads as a smooth line in Excel and a smooth dotted trace in Google Sheets
  (which draws the fit as markers). All five generators share the `/ 149` + `j < 150` pattern — keep them in step.
- **Helper values must be written as numbers, not text.** The standards `points` arrive from the client as
  *strings* (parsed out of the CSV); `_add_native_scatter_chart` coerces every `x`/`std_y`/`fit_y`
  to `float` (`_num()`, skipping non-numeric like `'NONE'`) before writing. A string cell makes Excel (a)
  refuse to plot it on the scatter — the green "number stored as text" marker — and (b) ignore the user's
  locale decimal separator. Write the bare `float` with **no explicit `number_format`** so the cell stays
  General and Excel renders the decimals per the user's own regional settings. **Anti-pattern**: do not write
  `p.get('x')` verbatim, and do not pin a decimal format on the helper cells. Covered by `tests/test_report_excel.py`.
- **Standards = blue diamonds, fit = red X-marks — markers only, and the fit must not be a native trendline.**
  The standards are blue **diamonds** (`Marker('diamond', size=8)`), the fit the 150-point sampling as red
  **X-marks** (`Marker('x', size=4)`); **neither series has a line** (`LineProperties.noFill = True`). Markers only
  on this category LineChart: the standards are sparse and never on adjacent rows (so nothing joins them), and the
  dense X-marks trace the curve, clearly distinct from the diamonds. Do
  **not** use an OOXML `Trendline` either: the chart plots **metric-vs-concentration** while the app fits
  **concentration-vs-metric** and *inverts* it (`buildCalibrationRegressionLine` — so a `logarithmic` fit draws
  an exponential curve, `exponential` a logarithmic one, `polynomial` a √-shape), meaning a native trendline
  would recompute the *wrong* functional family with its *own* coefficients, and **Michaelis-Menten has no
  native trendline type at all**. Markers show the app's true fitted curve everywhere with no per-algo casing.

### 2.24 Request-Origin Guard (CSRF + DNS-Rebinding)
- The app is single-user, has **no login/session and no CSRF token**, binds `127.0.0.1`, and is driven from
  the browser at an aliased host (`easyokapi.com` via the hosts file). Without a guard, any web page the user
  visits could issue a cross-origin `POST` to `http://127.0.0.1:<port>/` (or the alias) and trigger a
  state-changing route (`/delete_file`, `/edit_file`, `/shutdown`, …) — a simple form/`fetch` POST needs no
  CORS preflight — and a DNS-rebinding attacker domain could pose as same-origin.
- `src/security.py` `init_request_guard(app)` installs **one** `before_request` guard, registered **first**
  in `main.py` (before the activation/license gates), that for **unsafe methods** (POST/PUT/PATCH/DELETE):
  1. requires the **Host** the browser addressed to be a known hostname — loopback (`127.0.0.1`/`localhost`/
     `::1`) or the configured `--alias` (default `easyokapi.com`) — which blocks DNS rebinding (a rebound
     request carries `Host: attacker.com`); and
  2. requires the **Origin** (when present; else the **Referer**) to resolve to one of those hostnames — which
     blocks cross-origin CSRF (a cross-origin browser POST always sends `Origin`, so an *absent* Origin is not
     a cross-origin request and is allowed).
- Matching is **by hostname only** (scheme and port ignored): the app is the sole listener on its loopback
  port, so port-pinning adds no security, and hostname matching keeps the Flask test client (`Host: localhost`)
  and any custom `--alias` working with no special cases. **Anti-pattern**: do not add a state-changing **GET**
  (safe methods are unguarded by design); do not pin the guard to a specific port; do not exempt a POST route
  from the guard (all state changes originate from the app's own same-origin pages). Covered by
  `tests/test_security.py`.

### 2.25 Uninstaller Delivery Across Updates

- **The uninstaller must ship inside the update bundle.** On Windows `Uninstall.exe` lives **inside** the directory the in-app update swaps (`$INSTDIR`, beside `EasyOKAPI.exe` + `_internal`), so the swap would delete it. It used to be carried across from the old install unconditionally — which meant **every updated install kept the uninstaller it was first installed with, forever**, and no uninstaller fix could ever reach an existing user. `_WIN_SWAP_PS1` now **prefers `$live\Uninstall.exe` from the new bundle** and only carries the old one across when the bundle ships none (pre-1.3.x bundles, non-NSIS installs).
- **Getting an `Uninstall.exe` to bundle**: NSIS only emits one by **running** an installer (`WriteUninstaller` is a runtime instruction). `setup-frozen.nsi` therefore has a **`/DUNINSTALLER_ONLY`** compile mode: a tiny silent stub, no payload, whose only section is `WriteUninstaller "$INSTDIR\Uninstall.exe"`. CI compiles it, runs `make-uninstaller.exe /S /D=<outdir>`, and copies the result into `dist\EasyOKAPI\` **before** the bundle is zipped.
  - **Anti-pattern — a second copy of the uninstall logic**: do not write a separate `make-uninstaller.nsi`. The stub is the **same script** under an `!ifdef`, so the uninstaller it emits is the one a real install writes and there is nothing to drift. Keep `Section "Uninstall"` and `un.onInit` **outside** the `!ifndef UNINSTALLER_ONLY` guards — they are exactly what the stub exists to emit.
  - **CI must assert the artifact exists.** If the stub silently produces nothing, the swap script's fallback quietly carries the old uninstaller across and the regression ships unnoticed. The step fails hard when `Uninstall.exe` is missing. Order matters: generate **before** `Compress-Archive`.
  - `/D=` must be the **last** argument and **unquoted** — keep the output path space-free (`C:\uninst-out`).
- **An updater's fixes always land one cycle late.** The swap script is generated by the **currently running (old)** `update_service.py`, so a user updating *to* the first build with this fix is still driven by the old carry-forward logic; they get the bundled uninstaller on their **next** update. This is inherent to self-updating software — do not try to defeat it by having the app rewrite `%PROGRAMFILES%` itself (it runs non-elevated by design, §2.18; only the elevated swap helper may write there).
- **Linux has no uninstaller unless the installer installs one.** `install-frozen.sh` copies `uninstall.sh` into `/opt/EasyOKAPI/`; `build-tarball-frozen.sh` stages it. Without this a frozen Linux install has **no uninstall path at all** — the user hand-deletes `/opt/EasyOKAPI`, orphaning the udev rule and desktop entry and never releasing the license seat (§2.17). `uninstall.sh` serves **both** installs, so it must remove **both** udev rules (`99-easyokapi-hid.rules` from the source install, `99-easyokapi-cdc.rules` from the frozen one) and must **not** touch the frozen data root (`~/EasyOKAPI`).
- **On posix the uninstaller sits one level ABOVE the swapped dir — so it must be copied *up*, not carried across.** The Windows problem is inverted here. `_bundle_root()` is the dir holding the executable (`/opt/EasyOKAPI/EasyOKAPI/`, or `EasyOKAPI.app/Contents/Resources/EasyOKAPI/`), while the uninstaller lives in its **parent** (`/opt/EasyOKAPI/uninstall.sh`, `…/Resources/uninstall.command`). The swap therefore never touched it — it survived, but was **never updated either**, and an install predating the uninstaller never gained one. Both posix bundles now ship their uninstaller **inside** the onedir (CI copies it into `dist/EasyOKAPI/` before packaging) and `_build_posix_swap_script` copies it up into the parent after a successful swap.
  - Guard with `[ -f "$LIVE/$U" ] && [ -w "$PARENT" ]` and keep it **after** `rm -rf "$OLD"` and **before** the relaunch. It must never `exit` non-zero: `/opt` is root-owned while the app runs as the user, so an unwritable parent is the normal case on Linux and must not turn an already-applied swap into a failure.
  - Same prefer-bundled/else-keep-old semantics as Windows: a bundle shipping no uninstaller leaves the existing one untouched rather than deleting it.
  - **Anti-pattern — a self-deleting script without a re-exec guard**: a script that lives in the directory it deletes can be truncated mid-run (bash reads lazily). `uninstall.sh` and `installer-mac/uninstall.command` both copy themselves to `/tmp` and re-exec first. Resolve `$0` through `cd "$(dirname "$0")" && pwd` so the guard also fires on a **relative** invocation (`sudo ./uninstall.sh`).
- **macOS frozen remains a known gap**: `/Applications/EasyOKAPI.app` is removed by dragging to the Trash, which runs no script. `uninstall.command` serves the **source** install only.

### 2.26 Update Scratch Files Are Swept On Startup, Not On Exit

- **The update flow cannot clean up after itself.** The binary swap writes its helpers into the data root (`_update_swap.ps1`, `_update_coordinator.ps1`, `_update_swap_result.txt`, `_update_staging/`, and on posix one `mkstemp` `*_swap.sh` per update) and then **exits** so the detached helper can replace the install dir. There is no later point in that process to delete them, and nothing did — so every update left a growing pile in the user's `EasyOKAPI` folder.
- **Sweep on the next startup instead.** `update_service.cleanup_stale_artifacts()` runs from a `main.py` daemon thread beside `refresh_uninstall_entry()`. That fires exactly once per completed swap (the relaunched build clears its predecessor's mess) and also catches artifacts orphaned by a download that crashed mid-flight.
- **It MUST no-op while a swap is pending.** A failed or UAC-declined Windows swap deliberately keeps the staged bundle **and** the marker **and** the scripts so the next finalize can retry (§2.25, and the marker rule in `apply_pending_swap_and_exit`). Sweeping them would strand a downloaded update on disk with no way to apply it. The guard is `if read_pending_swap(): return`. A marker pointing at a **missing** staging dir is itself stale — `read_pending_swap()` returns `None` for it, so the sweep proceeds and drops the marker too.
- **Delete by explicit name or a distinctive glob — never by prefix sweep.** The data root also holds user data (`data/`, `json/`, `report/`, `user_settings.json`, `activation.json`). The posix swap script is written with an explicit `prefix='_update_'` so it can be globbed as `_update_*_swap.sh`; `mkstemp`'s default `tmp` prefix was too generic to delete on sight (the legacy `tmp*_swap.sh` pattern is swept too, for artifacts left by builds before the rename). Never widen this to `_update_*` alone — `_pending_update.txt` is load-bearing.
- Whole function is wrapped so it can never raise: a cleanup failure must not block startup.

### 2.27 Point-Mode Turn Axis (Turn vs Timestamp)

- **A raw series file's X column is either `Timestamp` (elapsed seconds, decimals) or `Turn` (a 1,2,3… measurement index, integers).** A `Turn` file **never** carries a `Timestamp` column — it is the point-mode alternative where the reference "point" is a turn number, not a time. Schema constants live in `src/file_path.py`: `CSV_SCHEMA_TIMESERIES` (`Timestamp,Value:1[..]`) and `CSV_SCHEMA_TIMESERIES_TURN` (`Turn,Value:1[..]`). `detect_csv_schema` recognizes both; `timeseries_x_column(header)` returns `'Turn'`/`'Timestamp'`/`None`; `is_multi_value_turn_csv_header` mirrors the Timestamp checker.
- **Read-side normalization is the single integration point.** The whole timeseries pipeline (plot, value-at-point, reports, merge) is keyed on the literal string `"Timestamp"`. Rather than teach every consumer a second X name, `file.get_dynamic_data()` **renames the `Turn` key to `Timestamp` on read** and returns `x_axis: 'turn'` (else `'time'`). On disk the file keeps its `Turn` header. Downstream JS reads `AppState.xAxis` to relabel the chart axis to `Turn` (integer ticks, no time-unit conversion — `generate-chart.js`) and to treat the point-mode reference as a raw turn index with **no** `getTimeUnitMultiplier` scaling (`data-handling.js` `updateRefCalPoint` / `processPointMode`). Do not "fix" the rename by threading a second X name through the pipeline.
- **The editor validator** (`_SCHEMA_VALIDATORS` in `file_routes.py`) has a distinct `CSV_SCHEMA_TIMESERIES_TURN` entry: same Value columns and metadata as the timeseries schema, but the first field is **integer-only** (`\d+`, no decimal) — a Turn index is never `1.5`.
- **Turn is point-mode only, everywhere in the UI.** The **Record as Turns** control (`#cdc-axis-control`) is in `MODE_VISIBILITY.point.show` / `.kinetics.hide` — hidden outside point mode. `navigation.js` `checkMeasHeader` accepts a `Turn,Value:…` header **only when `currentMeasurementMode === 'point'`** (kinetics keeps filtering Turn files out of the selectable list); it validates the X column (`Timestamp`, or `Turn` in point mode) then the `Value:N` columns.
- **Hiding the control is not enough — the Turn checkbox is actively DISABLED + unchecked outside point mode.** `runScript` reads `#cdc-axis-turn.checked` regardless of mode, so a control that is merely hidden but still checked (e.g. after switching point→kinetics with Turn on) would make a kinetics/calibrate CDC capture record `axis:'turn'`. `applyModeVisibility(mode)` (`index.js`) therefore, on **every** mode switch: in point mode re-arms the box from the saved `cdc_axis` default and enables it; in any other mode **unchecks and disables** it. `USER_SETTINGS.cdc_axis` is never mutated (the user's default is preserved and restored on returning to point). The startup init block (`init.js`, sets the box from `cdc_axis`) and the post-capture re-enable (`cdc-logging.js` `stopScript`) both mirror this: only arm/enable the box when `currentMeasurementMode === 'point'`. **Anti-pattern**: do not only hide `#cdc-axis-control` for a non-point mode — a hidden-but-checked box leaks the Turn axis into a kinetics/calibrate capture.
- **CDC capture picks the axis per session.** The reading panel has a **Record as Turns** checkbox (`#cdc-axis-turn`) whose default is the persisted `cdc_axis` user setting (`time`/`turn`; `user_settings.py` + App Settings → Colorimeter Reading). `runScript` sends `axis` to `/run_script`, which passes `--axis time|turn` to `log_cdc_data.py`. The collector sends an **`AXIS:` command between `TIMEOUT:` and `INTERVAL:`** (INTERVAL is the stage that starts the device talking, so the axis must be set first) and waits for `ACK_AXIS`; its header/data regexes accept either X column, and the log line is axis-aware (`Received: Turn:` / `Received: Timestamp:` — the JS data-point counter matches both).
- **Firmware is in lockstep** (`open_colorimeter_firmware/src/serial_manager.py`): `session_axis` set by `AXIS:turn`/`AXIS:time` (unknown → time); the header first column is `Turn` or `Timestamp`; a Turn row emits the post-increment `serial_count` (1,2,3…) instead of `written_time`. A new host requires a firmware that understands `AXIS:` (they ship together).
- **Converter:** the CSV editor shows a **Timestamps → Turns** button (`#convert-turn-btn`) only for a `#file-table` Timestamp series. It POSTs `/convert_timestamp_to_turn` (`{filename, path}`) which rewrites the saved file in place: header `Timestamp`→`Turn`, each row's first cell → its 1-based index; metadata and Value columns preserved. One-way and destructive (drops recorded times + unsaved editor edits), so the UI confirms first; refused while a capture is running.
- **Manual (on-demand) point-mode capture.** When **Record as Turns** is checked in point mode, a **Run mode** choice appears (`#cdc-run-mode-control`, radios `cdc-run-mode` = `auto`/`manual`; default is the persisted **`cdc_run_mode`** user setting, `user_settings.py` + App Settings → Colorimeter Reading + inline sync in `init.js`). **Automatic** is the normal interval-driven run. **Manual** makes the device idle and record **one Turn per press** of a **Measure now** button (`#measure-point-btn`): no interval, no timeout — the session ends only on **Stop** (`cdc-logging.js` hides the interval/timeout controls in manual). `runScript` sends `manual:true` to `/run_script`, which **forces the turn axis** and passes `--manual` to `log_cdc_data.py`.
- **Manual trigger is a file the logger polls — Flask never touches the port.** Because the logger subprocess owns the single serial port (§ CDC transport), a host **Measure now** press cannot write to the device directly. `POST /measure_point` (only while a session runs, else `409`) drops a trigger file (`log/measure_trigger.txt`); the logger's read loop (`log_cdc_data._check_measure_trigger`) consumes it and sends a `MEASURE` command (latency ≤ the `PORT_TIMEOUT` read cadence, 0.15 s — see §2.28). The button self-disables per press and re-arms when the requested row lands (`onNewDataPoint`, keyed on `manualSession`). The trigger is swept on run start (`hardware_routes.clear_measure_trigger` + `log_cdc_data.start`).
- **Firmware manual protocol is in lockstep** (`open_colorimeter_firmware/src/serial_manager.py`): the start chunk gains **`MANUAL:1`** (between `AXIS:` and `INTERVAL:`, ACK `ACK_MANUAL`) which sets `session_manual`; a manual session writes the header but `handle_serial_communication` **short-circuits** (no interval streaming, no timeout). The runtime command **`MEASURE`** emits exactly one row via the shared `_emit_row` helper, and is ignored unless a manual CDC session is live. Adding these commands means editing the firmware on **every branch** (`main`, `open-plus`, `open-uv`, `open-extra`) and the host (`log_cdc_data` command chain + `_send_start_commands` acks) together. A manual reading is always a turn, so manual implies the turn axis on both sides.
- **Turn calibration: each Turn is one standard (the whole standard curve is one file).** A Timestamp point file builds a calibration by reading each source's value **at a reference time**; a Turn file has no time, so the model flips — every recorded Turn is a distinct concentration standard and the `(Concentration, Value)` pairs across turns ARE the curve. When a **point-mode Turn file** is loaded (`AppState.xAxis === 'turn'`), `data-handling.js applyTurnCalUI()` **hides `#set-exp-point-section` and `#select-time-point`** (both time-point controls are meaningless) and shows **`#turn-cal-section`**: a per-Turn table (`renderTurnCalTable`) of `[Turn][Value:1…Value:N][Concentration input]` — the concentration is **shared per Turn** (one input, since each Turn is one standard), every source's value is shown. **Multi-source export**: the source(s) to write come from the existing **`#select-source-to-export`** multi-select (`getSelectedExportSources()`), NOT a dedicated picker — `exportTurnCal()` writes **one `Concentration,Value` file per selected source** (each source is its own curve; the single-Value cal schema is preserved downstream), filename suffixed `_source<N>` when more than one is selected, via parallel `/export_data` POSTs with **`xAxis:'turn'`** and one `entries` row per Turn that has both a concentration and a value for that source (each source needs ≥ 2 points). `exportData()` routes a Turn file to `exportTurnCal()`. **Anti-pattern**: do not write a multi-`Value` turn calibration file — the calibrate-mode reader, the fit, and the JSON export are all single-`Value`; multiple sources means multiple single-`Value` files.
- **Turn calibration schema is `Concentration,Value` (no TimePoint).** New constant **`CSV_SCHEMA_POINT_CAL_TURN`** in `src/file_path.py` (`detect_csv_schema` recognizes `Concentration,Value`); its editor validator in `_SCHEMA_VALIDATORS`. The **client-side** editor validator (`edit-file.js` `patternSets` for `#file-table`) must mirror the backend: it carries a `Turn,Value:…` series pattern (integer-only first column) **and** a `Concentration,Value` turn-cal pattern — keep the two in lockstep, and remember the `Turn` series pattern was missing before this feature, so any raw-Turn file also relies on it to be editable. `export_data.write_headers` / `extract_single_entry` take an **`x_axis`** arg (`'turn'` drops the TimePoint column); `/export_data` accepts `xAxis` and **refuses to append** a turn-based export to a time-based point file (and vice-versa — column counts differ). `measure.sort_csv_file` tolerates the missing index-2 (sorts by Concentration then Value). `navigation.checkMeasHeader`'s calibrate branch accepts **both** `Concentration,Value,TimePoint` and `Concentration,Value`. Manual creation: `/create_csv_file` takes **`cal_axis`** (`'turn'`/`'time'`) for a point calibration table — the **＋ New CSV** dialog (`createCsvFile`) offers a Time-series/Turn picker in calibrate-point mode and writes the 2-column turn template accordingly.
- **Point mode shows no kinetics analysis, and Turn files show no per-source concentration reader.** Point mode reads a single value at a point, so the Slope/maxRate/Saturation analysis table is not shown — `formatAnalysisHtml` returns `''` for `currentMeasurementMode === 'point'` (both render paths), the "Save Linearity Range" button is gated out of point mode, and the chart's maxRate/linear/saturation annotation lines were already `kinetics`-only (`createAnnotations`). Because there are no analysis panels to expand, the **Expand/Collapse-all-analyses** toggle (`#open-all-analysis-section`) is in `MODE_VISIBILITY.point.hide` (and in `kinetics`/`calibrate` `.show` so it returns). With the analysis panel gone, each source still needs its label: `groupMultiSourceRoutine` / `splitMultiSourceRoutine` render a plain **`Source N:` label** (in the source colour) in point mode with the per-source **🧮 Normalize** button beside it (in kinetics the label is part of `formatAnalysisHtml`). For a **Turn** file the concentration is assigned per Turn (the per-Turn calibration table), so the per-source **"Concentration from source-N sample"** reader (`concentration-reader-section-source-*`) is omitted (`AppState.xAxis === 'turn'` guard in `createChartSection` + `groupMultiSourceRoutine`) and the per-source **derived**-concentration sections are never un-hidden (`handleNonCalibrationMode` early-returns for turn — `processTurnDerive` renders the per-Turn derived table instead). **Anti-pattern**: do not render the kinetics analysis table or the per-source concentration reader for point/Turn — they mislead; concentration is per-Turn.
- **Turn ripples through the shared file features — audit them together.** (a) **Reports** (`report.js`): a point-mode calibration item is now detected as `isCalibrate && cols.includes('Value')` (a kinetics curve has no `Value` column) so a turn-based `Concentration,Value` file routes to the point branch, not the kinetics one; its `csv_columns` drop `TimePoint`. The rest of the point-report path is already time-point-tolerant (an empty/"all pooled" selection passes every row), so a turn file's turns pool into one curve. (b) **Merge** (`file.merge_csv_files`): raw **Turn** series join on the `Turn` index exactly like `Timestamp` (turn *cal* files merge via the `Concentration` branch); mixing Turn + Timestamp files still fails by design. (c) **Visibility**: `#turn-cal-section` is in every non-point mode's `MODE_VISIBILITY.hide` **and** `point.hide` (default hidden) — `applyTurnCalUI()` is the only thing that shows it, so it can't leak into kinetics/calibrate/report. (d) **Editor** validation mirrors backend (above). **Anti-pattern**: do not gate a point-calibration code path on the presence of a `TimePoint` column — key off `Value` and treat a missing `TimePoint` as the turn variant.
- **Replicate standards at one concentration are averaged for the fit; the value spread shows as error bars.** With Turn calibration a user can record several Turns at the *same* concentration (replicates). The **point-calibration fit averages the values per concentration** before computing coefficients — `calibrateRoutine` (`data-display.js`) runs `averageDuplicates(concentration, value)` and fits the one-point-per-concentration result, and the report point-fit paths do the same via `averagePointsByConcentration` (`report.js`, used by `getPointCalibrationData` and the finalize builders). **Do not rely on the server `map_duplicates` for this** — the calibration fit is `concentration = f(value)`, so the server groups by *value* (the x), which does not merge replicate values sharing a concentration; the averaging must be done client-side, grouping value by concentration. The chart already plots the per-concentration average and draws **min–max error bars** (`processData` → `distributionBarsPlugin` in `generate-chart.js`, active on every chart incl. calibration), so the fit, the plotted points, and the exported JSON/Excel coefficients are all consistent. (Kinetics calibration is unchanged — this is the point/Turn path.)
- **A Turn data file pairs only with a turn calibration curve (and a time-series file only with a time calibration) — enforced, and explained.** The CSV↔JSON identity now carries an **`axis`** field: `build_csv_identity` sets `'turn'`/`'time'` from the raw file's schema, `build_json_identity` sets `'turn'` for a curve with `x_axis:'turn'` and `'time'` for one carrying `time`/`time-unit` (kinetics/legacy → `None`, a wildcard). `identityMatch` blocks a turn↔time pair (`reason:'axis'`), so the non-matching row's **Select button is disabled** with a self-contained tooltip, and the `selectFile`/`revalidateActivePairing` backstops raise `identityClashText(...,'axis')` — a plain-language explanation of **why** (a time calibration derives concentration from the signal at a fixed time point, which a Turn file has no axis for; a turn calibration expects discrete turns). **Anti-pattern**: do not pair by Measurement/Unit/ConcenUnit alone in point mode — a turn file and a time-series calibration match on all three yet are physically incompatible; the `axis` gate is what separates them.
- **Turn calibration JSON omits `time`/`time-unit`; it records `x_axis:'turn'` instead.** In **calibrate/point** mode a turn-based cal CSV (`isTurnPointCal()` = point cal with no `TimePoint` column) hides `#select-time-point` and fits **Concentration vs Value directly** (no TimePoint filter); `exportJSONCoef` / `exportExcelFormula` skip the "time point required" guard and send **`x_axis:'turn'`** with `time:null`. `/export_cal_coefs` writes `{"x_axis":"turn"}` on the JSON (never `time`/`time-unit`) for a turn point curve. On the **derive** side, a turn cal JSON (`jsonFile.x_axis === 'turn'`) drives **`processTurnDerive()`** — a per-Turn table of derived concentrations (each Turn's value → the fit, no reference point), with the `#ref-point-line` hidden. Keep all three model implementations in lockstep as usual (§2.10).

### 2.28 CDC Port Selection, Line Framing, and Write Budgets

- **The PyBadge's two CDC ports are indistinguishable by USB metadata — the host MUST probe, never take the first match.** A board booted with `usb_cdc.enable(console=True, data=True)` enumerates **two** serial ports, and on macOS they report *identical* `vid`, `pid`, `description`, `hwid`, `serial_number`, `location` and `interface` (verified on 9.2.7/pybadge: only the `/dev/cu.usbmodem141**01**` vs `**03**` suffix differs). The old `connect_to_device()` took the first `comports()` match and `break`ed, so it landed on the **console (REPL)** port roughly half the time — commands are silently ignored there, and the session start failed as either a 15 s handshake timeout or an "Unexpected response" caused by stray console output (`loop_dt …`, tracebacks, `print()` from firmware debugging). **`connect_to_device()` now probes every vid/pid candidate** with a **`PING`** command and keeps the one that answers `ACK_PING` **or** `ERR_UNKNOWN` (`PROBE_REPLIES`); the console port answers neither. `ERR_UNKNOWN` is deliberately accepted so the probe works against **firmware predating the `PING` command** — do not tighten this to `ACK_PING` only until every field device is updated. **Anti-pattern**: do not re-introduce "first port with the right vid/pid wins", and do not try to disambiguate on `description`/`interface`/`location` — they are byte-identical.
- **`boot_for_CDC.py` ships `console=False` on every firmware branch.** One port means the ambiguity cannot arise at all; the probe is the belt to that braces, kept because developers legitimately run `console=True` to read `print()` output. `open-extra` shipped **no `boot_for_CDC.py` at all**, which is why the wrong-port failure was reported almost exclusively on the multi-sample build — nothing about multi-channel sensing was involved. Adding a branch means shipping its `boot_for_CDC.py`.
- **The device is not the bottleneck — do not "optimize" the firmware main loop for this.** Measured on `open-extra` with 3 active channels: the loop period is a flat **0.174 s** (min 0.172, max 0.192) whether idle, in a manual session, or streaming; a `MEASURE` round-trip is **~0.05 s**. Screen redraw, per-channel mux reads and `gc.collect()` do **not** grow with channel count. Perceived slowness was host-side read cadence, not firmware. Re-measure before believing otherwise (`print` the delta of `time.monotonic()` across `colorimeter.run()`'s loop body, read it on the console port).
- **Short port timeout REQUIRES buffered line assembly — never `readline()`.** The port timeout is `send_command.PORT_TIMEOUT` (**0.15 s**), short so the collector's loop can poll the manual-measure trigger promptly (it previously blocked up to 1 s per `readline()`, ~20× the device's actual response time). At that cadence pyserial's `readline()` returns **partial lines** on timeout, which then fail ACK matching or land as corrupt data rows. **`send_command.LineReader`** is the single fix: it reads `in_waiting` (or one byte, to pace the loop), buffers, and yields only complete `\n`-terminated lines. Both `send_command_and_wait_ack()` and `log_cdc_data`'s read loop use it. **Anti-pattern**: do not call `serial.readline()` anywhere on this port, and do not raise `PORT_TIMEOUT` back up to "fix" fragmentation — fragmentation is `LineReader`'s job.
- **The handshake ignores non-ACK lines and cleans up before retrying.** `send_command_and_wait_ack` retries the start chunk 3×. Previously, any line that was not the expected ACK was fatal — so a stray console line, a device banner, or a data row from a session that a *timed-out earlier attempt* had already started would kill the run. Now: lines outside `expected_acks ∪ error_acks` are logged and **skipped**, and each retry first sends **`0`** and drains, so the attempt starts against a known-idle device. A genuine `ERR_*` or a wrong-order ACK still fails **immediately without retrying** — that is device-side rejection, not a timing problem, and resending would only repeat it.
- **Firmware never blocks the main loop on USB, and never answers a blank line.** (a) `usb_cdc.data.write_timeout` is set to `constants.CDC_WRITE_TIMEOUT` — unset, `write()` waits forever once the host stops draining the buffer (logger killed, tab closed, port grabbed by another tool), freezing buttons, screen and everything else. (b) Because a bounded `write()` can return a **partial** write, all CDC output goes through **`SerialManager._write_cdc()`**, which pushes the remainder in a retry loop bounded by `constants.CDC_WRITE_DEADLINE` and then drops the rest — a lost row beats a hung device. Every ACK/ERR reply goes through `_reply()` → `_write_cdc()` for the same reason: a partially written `ACK_INTERVAL` desyncs the handshake. (c) `process_commands()` **skips blank command lines** (`if not command: continue`) — answering framing with `ERR_UNKNOWN` was itself a source of "Unexpected response" handshake failures. (d) It also no-ops when `usb_cdc.data` is `None` (boot did not enable the data channel) instead of raising every loop.
- **These are protocol timings, not user settings.** `PORT_TIMEOUT`, `PROBE_TIMEOUT`, `CDC_WRITE_TIMEOUT`, `CDC_WRITE_DEADLINE` are correctness-critical and must match the firmware's ~0.17 s loop period; they are deliberately **not** exposed in `user_settings.py` (§ Settings Coverage Rule) — a user-tuned value here breaks framing or the handshake.
- **Lockstep**: `PING`/`ACK_PING`, the blank-line skip and the write-budget changes live in `open_colorimeter_firmware/src/serial_manager.py` + `src/constants.py` and must be applied on **every branch** (`main`, `open-plus`, `open-uv`, `open-extra`), exactly like the `AXIS:`/`MANUAL:` commands (§2.27).

### 2.29 Pause / Resume a Live Reading

- **Pause holds a run; it never ends one.** `POST /pause_reading` / `POST /resume_reading` (409 when no session is running) put a live *automatic* capture on hold: the device stops taking readings, no rows are recorded, and the session, the output CSV and the logger subprocess all stay alive. Stop (`/terminate_script`) remains the only thing that ends a run — do not implement pause as stop-then-restart, which would open a second CSV and lose the series.
- **Same file-trigger IPC as `MEASURE`, but the file holds the desired STATE.** Flask cannot write to the serial port (the logger subprocess owns it — §2.27/§2.28), so the routes drop `log/control_trigger.txt` containing the token **`PAUSE`** or **`RESUME`**; `log_cdc_data._check_control_trigger()` consumes it in the read loop (latency ≤ `PORT_TIMEOUT`, 0.15 s) and forwards the command. Because the content is a state and not a bare flag, an unconsumed write is simply overwritten and **the last press wins** — the correct semantics for two opposite commands. Swept on run start by `hardware_routes.clear_control_trigger()` + `log_cdc_data.start()`, so a run never begins mid-pause.
- **The host-side gate is a fallback, and it must close FIRST.** `_check_control_trigger` sets `self.paused` *before* writing the command, and `process_data()` drops every row while paused. That covers (a) rows already in flight when the device sees `PAUSE`, and (b) **firmware predating the command**, which answers `ERR_UNKNOWN` and keeps streaming — the pause still holds, at the cost of a **gap in the Timestamp column**. `_handle_control_reply()` logs which of the two happened (`ACK_PAUSE`/`ACK_RESUME` vs the `ERR_UNKNOWN` that follows a `_pending_control`); a bare `ERR_UNKNOWN` with nothing pending stays an "Unexpected line".
- **The session clock FREEZES across a pause, on both sides.** Firmware `_resume_session()` shifts `serial_start_time` **and** `last_transmission_time` forward by the held duration, so the pause does not eat into the session timeout, the next row lands a full interval after the resume, and elapsed timestamps stay continuous. The client mirrors this exactly (`applyPausedState` shifts `sessionStartTime`/`lastDataPointTime`), so the on-screen elapsed/next clocks match the device. **Anti-pattern**: do not let either clock keep running through a pause — the two would disagree and the timeout would fire mid-hold.
- **Automatic runs only.** A manual point-mode run is already on-demand (nothing streams between presses), so it gets **Measure now** instead; `runScript` reveals the pause controls only in the `else` branch, and the two floating widgets are mutually exclusive by construction.
- **Two entry points, one state.** Inline `#pause-reading-btn` on the reading-panel button line, and the floating `#reading-control-fab` shown once that line scrolls out of view — same `IntersectionObserver` pattern as the Measure-now mirror (`startControlObserver`/`syncReadingFab`), same bottom-centre slot. `applyPauseControlsUI()` repaints **both**, so they can never disagree. `#session-paused-badge` says *Paused* in the timer widget, which is otherwise frozen and reads as stuck — that widget is now mounted only when the session strip is switched off (§2.33), and with the strip up the strip's own state readout carries this.
- **The floating bar leads with the session STATE, and that is the point of it.** At the scroll position where it appears, the control panel *and* the timer widget are both off-screen, so `#reading-control-fab` is the only thing that can say the run is alive: a breathing dot + monospace `RECORDING`/`PAUSED` readout (`.reading-fab-state`, `aria-live="polite"`), a hairline divider, then the actions. Paused stops the dot and rings it amber — a held session should look *held*, not busy. Do not reduce this back to two bare icon buttons; it would duplicate the inline controls while telling the user nothing.
- **Loudness is spent on the actions that change the run.** Pause keeps the neutral button skin (reversible, low-stakes); Resume takes `--success-gradient`, Stop takes `--danger-gradient`. Both floating and inline controls reuse the app's tokens (`--shadow-*`, the gradients, `#session-timer`'s translucent surface + monospace) rather than ad-hoc hex, and both are theme-aware.
- **Button skin is driven by custom properties, never competing `background` declarations.** `#reading-control-fab` sets `--btn-bg/-fg/-border/-shadow`; the theme overrides them on the *container*, the Resume/Stop variants on the *button*, which always wins over the inherited value. This is not a style preference — the app's global button reset is `button:not(.swal2-confirm):not(.swal2-deny):not(.swal2-styled)` at specificity **(0,3,1)**, so a plain `button.reading-fab-btn` (0,1,1) loses its padding/radius/background to it, and a `body.light #reading-control-fab .reading-fab-btn` (1,2,1) theme rule would in turn beat the `.reading-fab-danger` variant (1,2,0) and paint Stop neutral. **Anti-pattern**: adding a new themed button variant here with bare `background:`/`color:` declarations — anchor on the container ID and go through the vars.
- **Labels live in their own span, never on the button.** `data-i18n` writes `textContent`, so binding it to a button that also contains an icon erases the icon on every `applyTranslations()` pass. `_setToggleLabel()` writes the text **and** moves the `data-i18n` key onto the same span, so the Pause↔Resume wording survives a re-translate. Icon swap is pure CSS (`.icon-pause`/`.icon-play` toggled by `.paused` on the group / `.is-paused` on the inline button), so the markup is never rebuilt.
- **Quality floor**: `:focus-visible` rings on the floating actions, `prefers-reduced-motion` kills the dot animation and the hover lift (colour still carries the state), and the bar goes full-width above the AI chat widget under 600 px.
- **There is ONE floating transport design, used by both run kinds — keep them uniform.** `#reading-control-fab` (automatic: `RECORDING`/`PAUSED` + Pause/Resume + Stop) and `#measure-point-fab` (manual: `READY`/`MEASURING` + Measure now + Stop) share the same markup shape (`.reading-fab` > `.reading-fab-state` + `.reading-fab-divider` + `.reading-fab-btn`s), the same surface, the same bottom-centre slot, and the same CSS rules — every transport selector lists **both IDs** rather than collapsing to a shared class, because the ID is what beats the (0,3,1) global button reset. They are mutually exclusive by construction (a run is manual or automatic, never both). Measure now takes the same `--success-gradient` "go" slot as Resume; the manual bar's `.is-busy` state mirrors the automatic bar's `.paused` (dot stops, amber). **Anti-pattern**: restyling one bar without the other, or giving the manual bar its own bespoke pill — that divergence is exactly what this consolidation removed.
- **`state.reading_paused` is a UI-resync aid, not the source of truth.** The authoritative pause lives in the device + logger; the flag exists so `/check_status` can report `paused` and a client that missed a reply can self-heal. It is cleared on run start, terminate, and every session-end path.
- **Lockstep**: `PAUSE`/`RESUME` + `ACK_PAUSE`/`ACK_RESUME`, `session_paused`, the `handle_serial_communication` short-circuit and `_resume_session()` live in `open_colorimeter_firmware/src/serial_manager.py` and must be applied on **every branch** (`main`, `open-plus`, `open-uv`, `open-extra`) — exactly like `AXIS:`/`MANUAL:` (§2.27). Unlike those, the host degrades gracefully against older firmware (see the gate rule above), so the two do not have to ship together.

### 2.30 Reading Start-Up Notice and Start Timeout

- **`/run_script` returning `success` does NOT mean the device was reached.** It only means the logger subprocess survived its first 0.5 s (the window that catches `device_not_found`). Everything that actually establishes the session happens afterwards, in that subprocess: the CDC port probe (`PROBE_TIMEOUT` 1.5 s per candidate, §2.28), the command handshake (`send_command_and_wait_ack`, **3 attempts × 5 s**), and the firmware's `CONNECTION_WAIT_TIME` settle. None of it prints anything the user sees, so the panel used to sit silent for up to ~20 s and a perfectly good run looked frozen. **Anti-pattern**: treating the `/run_script` response as "recording has begun" in any user-facing copy.
- **Progress is read out of the logger's log lines, because there is no other channel.** The logger is a separate process and Flask never touches the port, so `#reading-startup` walks its phases from the text `fetchLogs()` already polls: *Looking for the colorimeter…* → `Connected to PyBadge at` → *Device found. Starting the session…* → `New session started` → *Session started. Waiting for the first reading…*. `STARTUP_PHASES` in `cdc-logging.js` holds those patterns — keep them in lockstep with `log_cdc_data.py`'s `self.log(...)` strings, which are load-bearing UI now, not just diagnostics. Phases only move forward (the log is cumulative, latest match wins).
- **The watch ends at the first data row, not at the header.** `onNewDataPoint()` calls `endStartupWatch()`; the session timer widget takes over from there. A run that reached `New session started` has proven the device is talking, so the notice never fights the interval countdown.
- **The timeout is bounded and configurable, and it stops the run.** `reading_start_timeout_sec` (`user_settings.py`, default **60 s**, clamped **10–600**) is the deadline for going live. On expiry the client stops the run through the shared `showTerminationNotice(..., 'error')` path — a session that never started writes no data, and leaving the logger attached holds the serial port. The floor of 10 s is deliberate: anything shorter fires during a normal handshake and would kill working runs. Halfway to the deadline the notice turns amber (`.is-late`) to say "slower than usual, still alive" rather than jumping straight to failure.
- **A failed start keeps its message; a successful one clears silently.** `endStartupWatch()` refuses to hide a `.is-failed` notice, because the teardown that a timeout triggers calls `resetRunControls()` → `endStartupWatch()` and would otherwise erase the explanation the user needs. The next `beginStartupWatch()` clears it.
- The elapsed counter is monospace like `#session-timer`, and it is the point of the widget — a number that keeps moving is what distinguishes "waiting" from "hung". Spinner is decorative and is disabled under `prefers-reduced-motion`.

### 2.31 Live Session Streaming (SSE)

- **A running session is PUSHED, not polled.** `GET /stream_session` (`src/live_stream.py`) tails the two files a run writes — the log (`state.log_file`) and the active CSV (path published in `log/current_output.txt`) — by **byte offset**, and emits SSE events `meta` / `rows` / `log` / `end`. It replaces two client clocks that ran regardless of whether anything changed: the 500 ms `/get_data` chart poll (full CSV reparse + full chart rebuild, twice a second) and the 2 s `/get_logs` poll (whole log file re-read, `Received:` counted by regex over the accumulated text). Latency is now one poll interval on the server, not up to 2 s on the client — which is what makes manual point mode's **Measure now** re-arm when its row lands rather than when a timer happens to fire.
- **The stream does NOT own the end of a run.** `/check_status` remains the single place that decides *why* a session ended, clears the log and resets `state.process`. `/stream_session` emits `end` and closes; the client calls `checkScriptStatus()` once from that event so the transition is prompt, not so it is duplicated. **Anti-pattern**: do not move end-of-session reasoning (`check_log_for_end_reason`, `clear_logs`) into the stream — two state machines racing over one log file is exactly the bug the `_terminationNoticeFired` guard exists to paper over.
- **Polling is the fallback, and it is selected by state, not by feature detection.** `index.js` guards both intervals with `liveStreamCarrying()`; `live-stream.js` sets that flag only once a frame has actually arrived and clears it on `onerror`. So a browser without `EventSource`, a stream that never opened, a reconnect gap, and `live_stream_enabled: false` all degrade to the old behaviour automatically, with no separate health check. `liveStreamCarrying()` is deliberately a `typeof` guard so a missing `live-stream.js` cannot throw inside a `setInterval` callback.
- **Only complete lines are ever shipped.** `_ByteTail` splits on `b'\n'` **before** decoding and holds the remainder in a buffer. This is not an optimisation — a row that is half-written when the generator stats the file would otherwise be pushed truncated, and a chunk boundary could land inside a multi-byte character (the `µ` of `ng/µL` in the metadata block). Same reasoning as `send_command.LineReader` on the serial port (§2.28). **Anti-pattern**: do not use text-mode `seek`/`tell` here — those offsets are opaque and cannot be arithmetic'd.
- **A file that shrank means "started over", not "corrupt".** `/check_status` blanks the log at session end and each run writes a new CSV, so `size < offset` resets the offset (and, for the CSV, re-derives the header) instead of erroring.
- **Row normalisation must match `file.get_dynamic_data` exactly.** `Turn` → `Timestamp` rename with `x_axis:'turn'` (§2.27), empty cell → `"NONE"`. The client feeds pushed rows into the **same** `processResponse()` a full fetch feeds, so any divergence would render live data differently from the same file reopened. Keep the two in lockstep.
- **The stream removes the fetch, not the redraw.** `renderLiveRows()` rebuilds through `processResponse()` rather than appending to Chart.js datasets directly, because the render path also recomputes the moving-average window, the source split, the kinetics analysis and the derived concentration — all of which depend on the whole series. Renders are coalesced (`LIVE_RENDER_MIN_MS`, 200 ms) so a burst of rows cannot queue a burst of rebuilds.
- **The finished file on disk is the authority.** `resetRunControls()` closes the stream and then calls `drawMeasurementChart()` once, so a row lost to a reconnect gap — or to `/check_status` winning the race to detect the end — cannot leave the chart showing less than was recorded.
- **The heartbeat is the disconnect detector.** A generator watching an idle session would otherwise never write, and never learn the tab is gone. `HEARTBEAT_SECONDS` (15 s) forces a comment frame whose failed write closes the generator. Do not remove it "because nothing is happening" — that is precisely when it is needed.
- **`live_stream_enabled`** (`user_settings.py`, default **True**, App Settings → Colorimeter Reading) is the escape hatch for a buffering intermediary that would hold SSE frames back; off falls back to the polls. `POLL_INTERVAL` / `HEARTBEAT_SECONDS` / `END_GRACE_SECONDS` are **not** user settings — they are sized against the firmware's ~0.174 s loop period (§2.28).

### 2.32 Background Music (online-only entertainment widget)

- **The audio never passes through Flask.** `GET /music/stations` (`src/routes/music_routes.py`) serves *metadata only* — the catalogue in `src/music.py` plus a connectivity verdict — and the browser's `<audio>` element connects straight to the broadcaster. The app therefore adds no bandwidth, no buffering layer, and no server-side codec dependency. **Anti-pattern**: do not proxy, re-stream, cache or record the audio through the app; that turns a link into a redistribution and puts a long-lived streaming response on a single-user Flask dev server that also has to serve a live reading.
- **Stations must be free, public, listener-supported streams** (SomaFM, Radio Paradise), referenced by the broadcaster's own published direct URL, and **https** — an `http` stream would be blocked as mixed content on any https-served page and leaks the listening habit in clear. Do not add a station that needs a key, a session, or an account.
- **Station ids are a persistence contract.** `music_station` stores the id, so renaming one in `STATIONS` silently resets that user's choice. `user_settings.save()` validates the id against the catalogue (`music.valid_station_id`), so a retired station can never be written back and left unplayable.
- **Online-only is enforced in three places, and each catches a different failure.** `navigator.onLine` is checked first (free, and definitive when it says *offline*); the server's `music.is_online()` TCP probe catches "connected to a captive Wi-Fi that goes nowhere"; the client's `CONNECT_TIMEOUT_MS` (12 s) catches a station that accepted the connection and then produced no audio. Without the last one the user gets a spinner forever, which is the failure mode the whole widget is meant to avoid.
- **The probe is TCP, not HTTP, and it is cached.** One round trip exercises the two things that actually fail (DNS and egress) and needs no response body. `PROBE_CACHE_SECONDS` (30 s) exists because the widget re-asks on every panel open *and* on every browser `online` event — uncached, that is a DNS lookup per click. Two hosts are tried before declaring offline: one broadcaster being down is not the machine being offline.
- **The widget mounts and unmounts; it is never merely hidden.** `OkapiMusic.refresh()` builds the DOM when enabled + online and removes it otherwise, and the `offline` event tears it down mid-session. A hidden-but-alive `<audio>` keeps the connection open and keeps buffering a stream nobody is listening to — which is also why `stop()` removes the `src` and calls `load()` rather than just pausing.
- **`music_enabled` defaults to `False`** (`user_settings.py`, App Settings → Background Music), with `music_station` / `music_volume` remembered alongside it. Default-off is deliberate: it is entertainment on an instrument app *and* it reaches the internet, neither of which a user should be opted into silently. Saving settings calls `OkapiMusic.refresh()` so the toggle takes effect without a reload; station/volume changes save themselves through the same `/settings` route, debounced (`SETTINGS_SAVE_DEBOUNCE_MS`) so one volume drag is one write.
- **Bottom-left is the widget's slot.** Bottom-right belongs to the AI assistant FAB and bottom-centre to the reading transport (§2.29); a fourth floating element must claim a free corner or it will cover a control that matters during a run.

#### 2.32.1 YouTube source (paste-a-link)

- **Embed only. Never extract.** Playback belongs to YouTube's IFrame player, which fetches everything itself. `music.resolve_youtube()` calls the keyless **oEmbed** endpoint purely to *name* a pasted link. **Anti-pattern**: any path that pulls the media itself — `yt-dlp`, a stream-URL scraper, a server-side download, a cache of the audio. That breaks YouTube's terms, and avoiding it is the reason this module is shaped the way it is.
- **The player stays visible while it plays**, at ≥200×200 — that is YouTube's requirement, not a design preference. The panel widens (`#okapi-music.is-youtube`, 372 px) and shows a 200 px-tall video pane. It follows that **closing the panel pauses YouTube** (`pausedByPanel`, resumed on reopen) and that **switching to the Radio tab stops it**, since both would otherwise leave a hidden iframe playing; radio is untouched by either, because background audio is the point there and there is nothing to see. **Anti-pattern**: hiding the iframe, shrinking it below 200 px, or covering it to get an "audio-only" player.
- **`.okapi-music-hidden` must stay a plain class rule.** It is applied to the panel, to each source section, and to the transport buttons that only exist for the queue; scoping it to one id (as `#okapi-music-panel.okapi-music-hidden` alone did) silently leaves both tabs' contents stacked on screen. It carries `!important` because the elements it hides set their own `display` at equal specificity.
- **No API key, therefore no search.** `search.list` costs 100 units of a 10,000/day quota, so a key shipped inside the app would be shared by every install and exhausted the same morning. Users paste a link; oEmbed names it for free. If search is ever added it must be on a key the *user* supplies, and the absence of one must degrade to exactly today's behaviour.
- **Spotify is not an option and should not be re-attempted.** Third-party playback needs the Web Playback SDK, which requires each listener to hold **Premium** and complete an OAuth login; the free tier streams nothing to outside apps and the 30-second `preview_url` is gone for new apps. "Spotify" and "free" cannot both hold.
- **Links are parsed and validated server-side.** `parse_youtube_ref()` accepts watch/`youtu.be`/`embed`/`shorts`/`music.youtube.com`/playlist forms and bare ids, and refuses anything off `_YT_HOSTS` — the widget embeds whatever comes back, so an unvetted host would be an open redirect into the player. A watch URL carrying both `v` and `list` is a **playlist**: that is what the address bar holds when the user copies it mid-playlist.
- **Naming is best-effort; parsing is not.** oEmbed refuses private, deleted and some region-locked items, and it is a network call that can just fail — so a failed lookup still returns the reference with a fallback title (a queue entry beats a refused paste), while unparseable text is a hard 400. The player reports the real reason (`onError` 101/150 = embedding disabled, 100 = gone, 2 = malformed) and the queue skips after `SKIP_AFTER_ERROR_MS`.
- **The queue lives server-side** in `music_queue.json` (`src/music_queue.py`), *not* in `localStorage`: a restart deliberately clears per-view `localStorage` (§2.20) and would wipe it. It is also not a `user_settings.py` key — it is content the user assembled, not a preference. The client owns ordering, so `POST /music/queue` replaces the list wholesale; add/remove/reorder are all that one write. Entries are key-filtered and string-coerced on load *and* save, because they are rendered into the DOM.
- **The IFrame API script loads lazily**, only when the user actually opens the YouTube tab — a radio-only user never contacts youtube.com. `_loadIframeApi()` chains onto any existing `window.onYouTubeIframeAPIReady` rather than overwriting it.
- **Loop/shuffle are ours, not the platform's** (`music_loop_mode`: `off`/`one`/`all`, default **all**; `music_shuffle`, default off) and they apply to the *queue*. A queue entry that is itself a YouTube playlist advances internally first; our `_advance()` only fires when the whole entry ends.

### 2.33 Visual Design System (tokens, materials, the session strip)

- **Every colour, font, radius and shadow comes from the token block at the top of `static/style.css`.** `:root` holds the light-mode values, `body.dark` re-steps them for graphite (dark is a *designed* mode, not an inversion: its own surfaces, its own ramp range, its own accent step). A new rule takes `--panel` / `--well` / `--hairline` / `--ink*` / `--accent*` / `--ramp-*`, never a raw hex. The old Tailwind-default greys + indigo/purple were remapped step-for-step into this scale, so a colour that was a background stayed a background — **anti-pattern**: reintroducing a bare hex (or a `linear-gradient`) in a rule instead of adding a token.
- **The palette is derived from the assay, not from light.** The device is a TSL2591 behind a cuvette on each active multiplexer channel; it reports absorbance and **has no selectable wavelength** (`open_colorimeter_firmware/src/light_sensor.py`, `constants.DEFAULT_ACTIVE_CHANNELS`). `--accent` is bromophenol blue — the dye a microalbumin colorimeter reads. **Anti-pattern**: any UI that names, picks or colour-codes a wavelength/nm value. The host never learns one: the CDC header block is exactly `# Measurement / # Unit / # Concentration / # ConcenUnit` plus `Timestamp|Turn,Value:1..N` (§2.10), and per-channel gain/integration time live on the device's own screens and are never transmitted. A "channel" in this app is a **source** — a mux channel index, `Value:N` — and that is the word the UI uses (§2.9).
- **Two material classes, and the difference is the layout.** *Chrome* (`.section`, the rail, fields, buttons) is flat, hairline-bounded, square-cornered, and does **not** lift or blur; *data* (the plot well, readouts, tables) gets the space and the only real elevation. Radius carries the distinction: `--r-flat` (0) for a data surface or a field, `--r-press` (4px) for something pressable — there is no third radius. `backdrop-filter` survives **only** on things that genuinely float over content (the spinner scrim, the AI and music panels, the reading transport); glass on a static panel is what made a checkbox group look as important as the chart.
- **Type: IBM Plex, self-hosted in `static/fonts/`** (`plex.css`, one face per weight per subset with the original `unicode-range`, imported by `style.css`). The app vendors every other dependency (`static/vendor/*`, §2.4) and must render the same offline, so there is **no Google Fonts `@import`** — regenerate from the css2 API and rewrite the `src` URLs. Three roles: `--font-ui` (Plex Sans) for prose and controls, `--font-mono` (Plex Mono, tabular figures) for **every measured value, field and axis tick** so digits stop shifting as a run streams, `--font-label` (Plex Sans Condensed, uppercase, tracked) for the panel-label voice. A `.section`'s `h2`/`h3` wears the label voice: it names a control group, so the only large type on the page belongs to the data.
- **Multi-source series are ORDERED, so they get a sequential ramp — never a cycled categorical palette.** The sources of one file are standards read through consecutive channels, so `--ramp-1..10` is a single hue stepped on lightness (validated: monotonic OKLab L, every step ≥ 3:1 against `--well`, end-to-end ΔE ≈ 30), and `sourceRamp(n)` in `index.js` spreads *n* series across those stops. `AppState.plotColors` is a **getter** over it (sized to `numSources`) so a theme switch repaints from the live tokens; `report.js` calls `sourceRamp(numSources)` for its own item counts. **Anti-pattern**: restoring the 16-entry rainbow, or hardcoding series hex anywhere — it discards the ordering that carries the concentration series.
- **Chart chrome states the data.** The main chart's title is `Measurement — filename` (metadata, so never translated — §2.22); a unitless y-axis falls back to the measurement name (`isNoneUnit()` compares case-insensitively, because the firmware writes `# Unit: None` and older files carry `NONE` — a blank or literal "None" axis label was the bug); ticks are mono, horizontal and thinned (`maxTicksLimit`); a series longer than 40 points drops its per-point markers so the trace reads as a shape.
- **The session strip (`#session-strip`) is the app's one ornament, and it is made of data.** A fixed 64px bar across the top draws the run in progress as a chart-recorder trace — one thin polyline per source in the same ramp steps as the chart — redrawn by `drawSessionStrip()` from `AppState.responseData`, which the SSE push and the fallback poll already keep current (§2.31). **It adds no fetching of its own**; do not give it a timer or a request. The pen advances left to right across the whole session rather than scrolling a window, so a flat trace means a flat reaction and not a rescaled view.
  - **The trace is the recording indicator.** `showSessionStrip()` reveals it on the first landed row (`onNewDataPoint`), `hideSessionStrip()` tears it down with the session timer, and `applyStripPausedState()` greys every line and freezes the advance when the run is held — so the state of a run is readable at **any** scroll position, which neither the timer widget (scrolls away) nor the floating transport (only appears once the control line has left the viewport) can promise. The floating transport keeps its own state readout regardless (§2.29): it owns the *actions*, and the two are painted from the same `readingPaused` flag so they cannot disagree.
  - **The strip subsumes `#session-timer`, which is now the fallback readout.** The strip carries the same three numbers (state, elapsed, next), so `onNewDataPoint` mounts the timer widget **only when the strip is off** (`timerEl.classList.toggle('hidden', stripEnabled())`) — two live clocks on one screen is one too many, and the redundant one is the one that scrolls away. **There is still exactly one clock**: `tickSessionTimer()` computes elapsed and the countdown once and writes both `session-*` and `strip-*` targets in the same pass, so they cannot drift. Its `#session-paused-badge` (§2.29) therefore only matters in that fallback mode; with the strip up, the strip's own state readout says *Paused*. **Anti-pattern**: giving the strip its own `setInterval`, or leaving both readouts mounted at once.
  - **A countdown needs something to count.** `#strip-next-field` hides itself whenever there is no interval (a manual point-mode run measures on demand), rather than showing a permanent `--:--`. `.urgent` (≤ 10 s to the next reading) is `--warn` on both readouts — imminence is a state, so it wears a status token.
  - **One shared y scale across sources, taken from the data**, plus a mono caption (`rows · sources · span · range`). A per-source scale would make two different absorbances look identical. Non-numeric cells (`OVFL`, `NONE`) break the polyline rather than being coerced to 0.
  - **The readout is honest about multi-source.** One source has an unambiguous latest value, so it shows it; with several there is no single true number, so it shows the row count (`strip.latest` / `strip.rows`). **Anti-pattern**: inventing an aggregate (a mean absorbance across different standards is not a measurement).
  - `body.strip-open` reserves the page's top padding **and** pushes `#top-right-controls` down; the bar is `position: fixed`, so forgetting either puts it over the User Guide button. Opt out with the **`session_strip_enabled`** setting (default on, App Settings → Colorimeter Reading).
- **The splash screen shows the instrument's own subject**: one hairline `.init-trace` curve of a saturating run, drawn once on load and disabled under `prefers-reduced-motion`. It replaced three blurred floating orbs, a shifting four-stop background gradient and a permanently shimmering pill CTA. Its type follows the ink tokens — the old near-white brand text was invisible once the surface became the light-mode well. **Anti-pattern**: ambient orbs, gradient meshes, or a shimmer sweep on a button; they say nothing about a photometer.
- **Loudness is spent on the data.** Hover changes a border and the ink, never the element's position (`translateY` lifts on every control made nothing feel clickable in particular). Filled accent is for the one primary action in a view; `--danger` for Shutdown is an outline that fills on hover; a utility like **Report a Bug** is a neutral outline, not an amber slab. Status tokens (`--danger` / `--warn` / `--go`) are reserved for state and are never reused as a series colour.

- **Dialog buttons wear the app's button language, and the role picks the colour — never the call site.** SweetAlert's buttons are the one control the sheet's blanket `button:not(.swal2-*)` rule deliberately skips, so they wore the stock palette until they were styled explicitly: `swal2-confirm` is the primary (filled `--accent`, the only filled control in the dialog), `swal2-cancel` is chrome (the way out is available, not advertised), and `swal2-deny` / a confirm carrying **`swal-danger`** is destructive in `--danger`. **Anti-pattern**: `confirmButtonColor: '#d33'` at a call site — ten dialogs had ten hand-picked hexes, which is how a delete and a save ended up the same green-vs-red coin toss; pass `customClass: { confirmButton: 'swal-danger' }` and let the token decide. Every colour rule needs `!important`, because SweetAlert writes `background-color` **inline** whenever a `*ButtonColor` option is passed. The styling is scoped to the instrument style, but **`swal-danger` is defined for classic too**: which button destroys something is meaning, not styling, so it does not belong to one visual language (classic sets `background`, not `background-color` — it redefines `--danger-gradient` as a `linear-gradient`, which `background-color` silently rejects and renders blank).

### 2.34 Interface Style Switch (`ui_style`: instrument | classic)

- **The redesign is switchable, and the switch is a scoped override layer — not a second stylesheet.** `ui_style` (`user_settings.py`, default **`instrument`**, App Settings → General) selects the visual language. `instrument` is the design in §2.33; **`classic`** is the previous look — Tailwind greys + the indigo/purple gradients, translucent blurred cards with a hover lift, 12px radius everywhere, Inter/Outfit, headline-weight panel headings, the 16-colour categorical series palette, the pill theme toggle, the orb splash. It is one `body.ui-classic` block at the end of `style.css` that restores those *values* plus the handful of material rules the instrument style flattened. **Anti-pattern**: forking `style.css` into two sheets, or adding a third style — the whole point of tokenising was that a look is a set of values.
- **The classic layer is GENERATED, because a token override alone is not enough.** The redesign rewrote ~519 colour literals *inside* rules — `body.dark { background-color: #111827 }` became `#0e1113` — and **a custom property cannot override a concrete declaration**, so redefining `--bg` restored only the parts of the old look that happened to read from tokens. (Symptom: classic came up with the graphite background and the accent-outlined mode chip instead of #111827 and the yellow one.) `tools/gen_classic_style.py` walks the released stylesheet and the current one and emits an override for every declaration whose value actually differs, scoped under `body.ui-classic`, between the `BEGIN/END GENERATED CLASSIC LAYER` markers in `style.css`. Regenerate after touching any shared rule:
  ```
  git show a544ab1:static/style.css > /tmp/ref.css        # v1.3.11
  python3 tools/gen_classic_style.py /tmp/ref.css static/style.css /tmp/classic.css
  ```
  Two things the generator cannot do, which are therefore hand-written and must be kept in step: (a) **legacy alias tokens** (`--text-color-*`, `--table-border-*`, `--chart-*`, `--scrollbar-*`, `--primary-color`) — rules reading them are byte-identical in both sheets, only the *value* moved, so they are restored in the `body.ui-classic` token block; (b) **rules the redesign added** (the label-voice `.section > h2`, mono fields, the squared toggle, the filled `#run-script-btn`, the tinted User Guide / Report a Bug, `#chart-container`'s square well) — there is nothing in v1.3.11 to diff them against, so they are undone by the reset block after the END marker.
- **v1.3.11 writes theme rules two ways — `body.dark X` *and* a bare `.dark X`.** Both mean the class on `<body>`, so `scope()` folds a leading `.dark`/`.light` into the body compound (`body.ui-classic.dark X`); treating it as an ancestor silently dropped 35 rules, which is why the dark table header and the dark toggle knob came back wrong the first time.
- **Verification is a computed-style diff, not an eyeball.** Load the app, apply `body.ui-classic`, snapshot `getComputedStyle` for a list of selectors, swap the `<link>` to the released sheet with the class off, snapshot again, and compare. The two styles now agree on every compared property in both themes; the only residual difference is `#run-script-btn`'s border colour, which is the `blink` keyframe sampled at different instants (it swings 0.02→0.99 between samples in either style). Re-run this after regenerating.
- **The class is stamped server-side.** `index.html`'s `<body class="{{ 'ui-classic' if user_settings.get('ui_style') == 'classic' else '' }}">` means the page never paints one style and then swaps to the other. `init.js` only ever *toggles* `dark`/`light`, so it cannot clobber it. Changing the setting **reloads** (same reason `ui_language` does): the class comes from the render, and the chart palette and the strip read the style when they build.
- **The Windows splash launcher follows `ui_style` too.** It is the first thing on screen and it must not contradict the window opening behind it, so `installer-win/launcher-frozen.ps1` (frozen build) and `installer-win/launcher.ps1` (source install) each hold **two complete XAML templates** and pick one in `Get-UiStyle`. Two templates rather than colour placeholders, so the classic splash stays byte-identical to what shipped — verified by diffing it against the released file.
  - **Resolve the settings file the way the app does, per build.** Frozen: `<Documents>\EasyOKAPI\user_settings.json`, unless `<Documents>\.easyokapi_dataroot` holds an absolute path (the relocatable data root, §2.19) — the pointer sits *beside* the default folder, not inside it. Source install: `.\code\user_settings.json`, the same `.\code` this launcher already uses for `main.py` and the venv. **Anti-pattern**: assuming the settings file sits next to the executable; a user who relocated their data root would get the wrong splash.
  - **Fail open to instrument.** Missing file, unreadable JSON, no `ui_style`, no Documents folder — every path returns `instrument`. A splash is decoration; it must never be the reason a launch fails, so the whole lookup lives in one `try`/`catch`.
  - `$script:ScriptDir` is resolved at the top of the file, above `Get-UiStyle`, because inside a function `$MyInvocation.MyCommand.Path` describes the *function call*, not the script.
  - Both templates must keep the four `Name=`d elements the script looks up (`ProgressTrack`, `ProgressFill`, `StatusLabel`, `PctLabel`) — a `FindName` miss is a null-reference at the first timer tick, on a window the user is staring at.
- **JS reads the class, never the setting.** `isClassicUI()` (`index.js`) tests `document.body.classList` — correct even before `USER_SETTINGS` exists, and it can never disagree with what is on screen. Two consumers branch on it: `sourceRamp()` returns `CLASSIC_PLOT_COLORS` (the original 16 entries) instead of the sequential ramp, and `stripEnabled()` returns false so the **session strip stays down and the top-right timer widget comes back** — that is what "the previous UI" means (§2.33 makes the widget the fallback readout; here it is the only one). CSS hides the strip too, as belt and braces.
- **Correctness is not part of the style, and is never reverted by it.** The y-axis that read literally "None" for a unitless measurement, the chart title that named the app's action rather than the data, the marker-drop past 40 points, and the self-hosted fonts are fixes — `classic` keeps them. Only *look* is switched. **Anti-pattern**: putting a bug fix behind the style flag.
- **Both styles' fonts are vendored.** `static/fonts/plex.css` (IBM Plex, instrument) and `static/fonts/classic.css` (Inter + Outfit, classic) are both `@import`ed by `style.css`; the inactive family costs nothing because `unicode-range` + the family never being requested means no file is fetched. The classic look must not reintroduce a Google Fonts request (§2.4).
- **Splash markup carries both.** The `.init-orb` divs live in `index.html` but are `display: none` unless `body.ui-classic`; the instrument `.init-trace` is hidden in the other direction. Keeping the markup for both is what lets the switch be CSS-only.
- **Standalone pages follow the style too, but they branch server-side instead of overlaying.** `templates/goodbye.html` (`/shutdown`) is the first of these: the route reads `ui_style` from `user_settings` and the template holds **two complete CSS + markup blocks**, exactly like the Windows splash launcher — `{% if ui_style == 'classic' %}` keeps the shipped orb/glass card byte-for-byte, `{% else %}` is the instrument panel (flat, hairline-bounded, a chart-recorder trace that runs once and parks, condensed uppercase labels, a mono tabular countdown draining a 2 px hairline bar). The generated `body.ui-classic` layer is not usable here: it is scoped to `style.css`, and these pages deliberately do **not** load `style.css` — 5000 lines of app layout on a 460 px card is the wrong inheritance. So the instrument block **copies the token values** from the top of `style.css`; keep the two in step when a token moves. The template tests only for `'classic'`, so an unexpected stored value renders instrument rather than reaching the markup — the same fail-open rule the splash uses. The shutdown page ends the session, so it is drawn as the last frame of one: a parked pen, not a green checkmark.
- **A standalone page must render offline.** `goodbye.html` used `@import url('https://fonts.googleapis.com/…Inter…')`, so on a machine with no network the shutdown screen fell back to a system font (§2.4). Both branches now link the vendored sheet for the family they use — `static/fonts/plex.css` (instrument) or `static/fonts/classic.css` (classic). **The remaining standalone pages still carry that import and are still classic-only**: `restarting.html`, `restart_required.html`, `activate.html`, `license_blocked.html`, `license_banned.html`, `license_reverify.html`. Convert them the same way when they are next touched.
- Covered by `TestUiStyle` in `tests/test_user_settings.py`: the value is a **closed choice** (`instrument`/`classic`, trimmed + lower-cased), and an unknown value leaves the stored one untouched — it is written straight into a class attribute, so it must never reach the template unvalidated.

### 2.35 Virtual Controller (the device's keypad, on screen)

- **The port still has exactly one owner — the controller is idle-time only.** §2.27/§2.28/§2.29 say Flask never touches the serial port because the logger subprocess owns it; `src/device_link.py` is the other half of that rule, not an exception to it. It opens the port **only while no reading session is running**, and every controller route (`GET /device/state`, `POST /device/button`, `POST /device/channels`) answers **409 `busy`** the moment `state.process` is alive. `/run_script` calls `device_link.link.close()` **before** spawning the logger, because the logger cannot wait its turn. **Anti-pattern**: adding a trigger-file path so the controller keeps working mid-run — the controls that make sense during a recording (pause, stop, measure) already have routes, and a blank or a gain change underneath a run silently invalidates it.
- **The connection is held between commands, and reaped when idle.** Opening the port costs a settle delay plus the PING probe that tells the CDC *data* endpoint from the byte-identical console endpoint (§2.28) — about half a second, which is the difference between a button pad and a form submission. So `DeviceLink` keeps the handle, and a daemon reaper drops it after `IDLE_TIMEOUT` (30 s) with no command, so a firmware update or a serial monitor can claim the port on a machine where the app is merely open. `command()` retries **once on a fresh connection**: a device unplugged and replugged leaves a handle that writes without error and never answers, and without the retry the controller stays dead until the app restarts.
- **`STATE?` is `key=value;` text, not JSON, and the field list is identical on all four firmware branches.** The device guards every screen allocation against MemoryError; a few string joins cost far less than a dict plus a serializer. Fields a build has no notion of (`chans` on a single-sensor board) are sent **empty rather than omitted**, so `device_link.parse_state()` is one parser for every device. Keep `SerialManager._state_line()` (all branches) and `_STATE_INTS`/`_STATE_INT_LISTS`/`_STATE_TEXT_LISTS` in lockstep. `""` means *not applicable* and must not become `0`.
- **What a button does is read from the device, never assumed.** The panel's real job is labelling: `menu` saves in Settings, opens the menu in Measure, dismisses a message, and the keypad itself cannot say which. `DEVICE_BUTTON_FUNCTIONS` in `static/script/device-control.js` mirrors the firmware's mode handlers — **a label that lies is worse than no label**, so the two move together. Buttons with no effect on the current screen stay visible but dimmed; knowing that Up does nothing here is part of what the panel is for.
- **The keypad is laid out as the board is, and each key wears the board's own silkscreen mark.** The panel is read against the instrument in the operator's hands, so position is half the label: the readout is the **screen**, in the middle column, with **SELECT** (`menu`) top-left and **START** (`blank`) top-right, the d-pad down its left side and **A** (`itime`) / **B** (`gain`) down its right, staggered because they sit diagonally on the board (A above and right of B). Source of truth is the photo in `open_colorimeter_firmware/images/Measure.jpeg` plus `colorimeter.button_map`, which is keyed by the PyBadge shift-register order in `constants.BUTTON` (bit0 B, bit1 A, bit2 START, bit3 SELECT, bits 4–7 the d-pad). `glyph` in `DEVICE_BUTTONS` is therefore the silkscreen mark, **not** a mnemonic for the firmware role — the old `B` for *blank* named the key marked START and sat opposite the key actually marked B. **Anti-pattern**: stacking the four non-d-pad keys in one column because their labels are words; a control that mirrors the hardware needs no legend, and one that does not is a legend that lies. The keypad's rules are scoped four classes deep on purpose (`.devctl-body .devctl-keypad .devctl-cluster .devctl-btn`): the sheet's blanket `button:not(.swal2-*)` rule is `(0,3,1)`, and it centres its content and drops the generic disabled fill over the idle keys.
- **A key is a fixed box (`--devctl-key-w` / `--devctl-key-h`), and its label is one line.** The keypad is a map of the board, so keys sized by whatever they happen to say on the current screen — a d-pad that changes shape when the device leaves Measure — stop being one. A label wider than the box **scrolls through it on a loop** (`setDeviceButtonLabel()` measures once per label change and sets `--devctl-marquee-shift`/`-time`; two copies chase each other so there is no blank sweep), pauses on hover, and is dropped entirely under `prefers-reduced-motion`. Idle keys never scroll — eight labels moving at once is noise, and a key that does nothing on this screen is not the one worth reading. The `data-hint` tooltip always carries the whole string (and the firmware's own name for the button, which the keycap no longer has room for), so **nothing depends on catching the marquee at the right moment**. **Anti-pattern**: re-writing the label on every poll — that restarts the animation every 1.5 s and the text never gets far enough to read, which is why the label itself is the cache key.
- **Too narrow for three columns, the face folds into one — it does not reflow into something else.** The fold is a **container query on the panel** (`container-type: inline-size` on `.devctl-body`), not a media query: this section can be narrow inside a wide window, and page zoom moves the two apart — which is exactly the case where the squeezed three-column face pushed the screen off the panel. Under 620 px of panel the face becomes three **bands** in the order it is read across the board — the left-hand keys, the screen, the right-hand keys — and each band keeps its keys on **one line**: the d-pad cross flattens to `◀ ▲ ▼ ▶` beside SELECT, and START sits with B and A. A band per region is still a map of the board; a key per row is a list. (A/B are placed by grid area there, not by the wide layout's stagger margin — without the assignment they auto-flow in DOM order and A lands left of B.) The threshold is a hair over what three columns actually need, so the face stays whole wherever it fits — which requires `.devctl-body` to cap its column at `minmax(0, 1fr)`: with an `auto` column the grid sizes to the face's max-content, so a keypad wider than the panel hangs off its right edge *and* reports no overflow, because its scroll box is then exactly as wide as its content. The `@media` copy is the fallback for browsers without container queries, and the sideways scroll (with the keypad's own hairline scrollbar) is the last resort below that, not the narrow-window plan. **Anti-pattern**: collapsing the keypad into a list of buttons — a list is a legend, and the panel exists precisely so no legend is needed.
- **The menu bar is the device's own menu, asked for — never guessed.** The entries are the default measurements plus **every key in that device's `calibrations.json`** plus Concentration / About / Settings, all built on the board, so the host cannot derive them: `GET /device/menu` sends `MENU?` and the firmware answers one `MENUITEMS a,b,c` line. Clicking one sends `POST /device/menu` → `MENU:<index>`, which sets `menu_item_pos` and runs the **firmware's own menu handler**, so opening an entry from the app does exactly what choosing it on the keypad does — not a second implementation of what each entry means. The list is fetched **once per connection**, not on the 1.5 s state poll: it changes only when the device reboots, and `menupos` (which does move) already rides in the state. The bar marks two different facts — the entry the device has **open** and the entry its keypad **cursor** rests on. It is gated on the `menu` capability, so a build predating the command shows no bar rather than a bar that opens the wrong screen. `MENU:` is refused mid-session for the same reason `BTN:` is, and a name containing a comma is stripped on the device: the separator would otherwise invent an entry and shift every index after it.
- **Concentration is set whole, and only on the screen it belongs to.** The device's keypad can only *step* the value (+1 / +10 / +100 and back), so 250 ng/µL was twelve presses from the host; `CONC:<value>[,<unit>]` sends it outright and `CONC?` lists the units (asked for, never hardcoded — offering a unit the firmware does not know would have every set refused). The panel is mounted **only while `mode === 'CONCENTRATION'`**, because that is the screen the value belongs to and the same rule the device follows; leaving the screen drops a half-typed edit with it. **Unknown is a value, not a blank**: it is what the screen shows before one is dialled in, so `null` from the client and `none` on the wire mean it explicitly, and an empty box is refused with a pointer to the Unknown button rather than guessed at. Setting writes the screen **and** commits to `colorimeter.concentration` — the keypad's save minus the "Concentration saved" message screen, because a host press cannot dismiss that screen and would strand the device waiting for a finger. Negatives are refused on both sides (the keypad clamps at zero, so no operator can reach one) and a whole float is stored as an int so `12.0` still reads `12`. While the operator is typing, the 1.5 s poll stops writing the fields (`deviceConcDirty`) — otherwise it overwrites a half-typed value with the device's.
- **A host command that touches a screen is queued, not run where it arrives.** Building or repainting a screen from inside the serial handler runs three frames deeper than a keypad press (`handle_serial_communication → process_commands → …`) and with whatever heap the command left. Deep and tight, the PCF font stops loading the glyphs it has not already cached and the screen comes out **missing letters** — "Menu" drawn as "enu", "Unknown" as "nnown" — while building a MessageScreen that deep raises outright, which is why About looked unreachable from the app. So `MENU:`, `CONC:` and `TIMING:` **validate, queue, and answer**; `colorimeter.run()` drains the queue through `SerialManager.apply_pending()` on the shallow stack, between frames. The ACK therefore precedes the work by ~0.17 s, so `device_link` waits `SETTLE_AFTER_QUEUED` before the state read that rides back with it. **Anti-pattern**: doing screen work in a command handler because it "worked on the bench" — it works until the heap is a little tighter, and then it silently drops glyphs rather than failing.
- **The Settings form sets the device's pair whole (`TIMING?` / `TIMING:`)**, mounted only while `mode === 'SETTINGS'` — the same rule the concentration form follows. Timeout **`null` means no timeout**, a real setting rather than a missing field: the run then goes until it is stopped. The device owns the legality rule — the timeout must outlast the interval, or a run times out before its first reading — and its refusal text is what the operator sees, because "timeout is not longer than the interval" is the only part they can act on. Units come from `constants.TIMING_UNITS`, read rather than guessed, and applying also rewrites the settings screen's *saved* copy so its Revert button cannot undo a change made deliberately from the app.
- **Sensor calibration is measured, not typed (`CALIB?` / `CALIB:` / `CALIBRATE`)**, mounted only while `mode === 'CALIBRATION'` — the same rule the concentration and settings forms follow. Two channels looking at the same LED through the same cuvette do not report the same count: the TSL2591's responsivity has a part-to-part spread, and each holder aims its own LED at its own sensor with its own alignment and stray-light path. `raw_count_factor` in the device's `configuration.json` is one multiplier per **multiplexer channel** — keyed to the holder, not to a position in `chans`, so a `CHANNELS:` change cannot hand channel 3's factor to channel 0. `CALIBRATE` samples every active channel and normalizes them to their own **mean** (`factor[c] = mean / median[c]`): normalizing to the brightest would scale the rest up and amplify their noise, to the dimmest would throw away the good channels' headroom. It measures the *uncorrected* counts — reading through the factors it is about to replace would just return the ones already loaded — and refuses anything outside 0.1..10x, naming the channel, because that far off is a dead LED or a cuvette left in a slot, not part spread. Alone among the device commands it is **synchronous**: the host is holding the port waiting for the numbers, so the firmware uses its short sample count to stay inside `REPLY_TIMEOUT` and answers `CALFACTORS` rather than an ACK the host would have to chase with a read. Changing the factors **rescales the blanks** by the same ratio rather than dropping them — a blank carries whatever factor was in force when it was taken, and a constant multiplier rescales exactly, so the operator keeps the blank they took. Two views of one array, deliberately: `CALIB?` answers **all** multiplexer channels (the shape `configuration.json` holds — writing back only the active ones would blank every idle holder's factor), while `STATE`'s `rcf` is the **active** channels in stream order, beside `gains` and `itimes`. Runtime-only for the same reason `CHANNELS:` is, so the panel shows the array verbatim to be copied into the file. **The procedure is printed in the panel, not filed in a manual**: this is the one control here whose result depends on what the operator physically did to the instrument *before* pressing it — same contents in every holder, same LED, nothing saturated — and a button that silently produces garbage from a wrong setup needs its preconditions where the button is. The steps carry the failure modes with them (a refused holder names the slot) and end with the copy-into-`configuration.json` step, because a calibration the operator believes is saved and is not is worse than none. **Fewer than two active channels and the pass is refused, on both sides.** The factors are relative — each channel is scaled onto the others' mean — so with one channel the arithmetic returns 1.0 and looks like a device that needed no correction, which is the one wrong answer worth guarding against. The firmware says `only channel 0 active: need 2 to compare`; the panel hides nothing and instead disables Calibrate and explains why, because an enabled button that always fails reads as a broken device. Clear stays live: factors already loaded are still in force on whichever channel is active. **Note what it does not do**: absorbance and transmittance divide each channel by its own blank, which cancels a constant multiplier — this changes Raw Count, Irradiance and cross-holder comparison, and an absorbance that still disagrees after it has a different cause. Full write-up in the firmware's `raw_count_calibration.md`.
- **Where builds genuinely differ, the firmware says so in `caps`, and the host branches on that — never on a version number.** `btn,state` everywhere; `channels` only where the multiplexer channels are selectable (open-extra); `selsensor` where Right picks the sensor gain/itime act on (open-extra, open-plus); `uvchannel` where Right steps the sensor's own spectral channel (open-uv). Right in MEASURE is resolved from `caps` in `deviceButtonFunction()` rather than from the table, because it is the one button whose *meaning* — not just availability — changes between devices.
- **`BTN:left` in MEASURE mode is refused by the firmware.** There it toggles the device's HID keyboard fallback, which types readings into whichever window has focus on the host machine. A host that wants a recording has `/run_script`; the panel shows the button as unavailable and says why.
- **`CHANNELS:` is runtime-only, and refused mid-session.** `Colorimeter.set_active_channels()` (open-extra) rebuilds the sensors, the gain/itime cycles, the blanks and the measure screen — whose row count is fixed at allocation, hence `clear_all_screens()` **plus** `active_screen = None`, or the manager keeps comparing against a screen it just dropped. Nothing is swapped in until every requested sensor has answered. `is_blanked` is dropped: a blank belongs to the cuvette that took it. It is refused while a session is live because **the channel count is the column count** of the header the host already parsed. It does **not** rewrite `configuration.json`: CircuitPython mounts its own filesystem read-only unless `boot.py` remounts it, and doing that would take the CIRCUITPY drive away from the host — a power cycle returns the device to its configured channels, and the UI says so.
- **The connection switch parks the port without closing the panel.** `device_link_enabled` (default **on**) is the checkbox beside the status strip, and it is *not* the same knob as `device_control_enabled`: that one hides the feature, this one decides whether the app may hold the port while the panel is open — the state to be in when a firmware update or a serial monitor wants the device. Turning it off stops the poll **and** calls `POST /device/disconnect` (`device_link.link.close()`) rather than leaving the port to the 30 s idle reaper: someone who flips this is usually about to hand the port over, and a switch that appears to do nothing for half a minute gets flipped again. The gate lives inside `startDevicePolling()` so no path can start a poll behind the user's back, and the position persists, because a user who parked the port for a firmware update should not find the app holding it again after a reload.
- **Polling starts when the panel is expanded, and only then.** The section is collapsed on load, so a user who never opens it never opens the port. One request in flight at a time (`devicePollInFlight`) — a slow reply must not queue a backlog of stale answers — and the poll stops on `visibilitychange` when the tab is hidden. `device_control_enabled` (default **on**) hides the panel outright; `device_state_poll_ms` (default **1500**, 500–10000) sets the cadence, floored because the firmware loop is ~174 ms and a `STATE?` reply is one round trip. **Anti-pattern**: giving the panel an SSE stream — the device answers questions, it does not push.
- Covered by `tests/test_device_link.py`: STATE parsing (typed fields, `OVFL` verbatim, empty ≠ zero), the reply handling of each operation, the non-reply skip, the reconnect retry, the 409 on every route during a session, that `/run_script` releases the port first, and the calibration commands (payload format, the device's refusal text surfacing, run vs write vs clear on one route).
